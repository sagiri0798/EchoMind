# Agent 开发面经题库：EchoMind 项目版答案

标记说明：`【已实现】` 表示 Python 或 Java 项目中有对应代码；`【部分实现】` 表示有保护框架或缩小版能力，但不能夸大为完整方案；`【项目未涉及】` 表示当前项目没有这类技术，后面的通用答案是面试时可采用的方案。

## 一、MCP / Skill / 工具调用层

### 1.1 三分法

- **Q：内部接口如何封装成 MCP？Schema、错误信息、流式返回、版本兼容性怎么处理？**

  **A：【部分实现】** 项目把知识库查询封装成标准 MCP Tool，并通过外部 MCP Client 接入 Microsoft Learn 等工具。Schema 使用 JSON Schema，参数在调用前校验；错误统一返回可被模型理解的结构，如 `success=false`、`error_code`、`message`、`retryable`，不把堆栈和密钥返回给模型。工具名和核心字段保持稳定，Schema 只做向后兼容的增量扩展，破坏性变更通过版本化工具名并存。当前 MCP 工具结果不是流式返回，而是按大小上限返回完整 JSON；长任务若要流式化，应使用 MCP progress notification，或返回 `job_id` 并提供查询、取消接口，避免把协议流和大模型流混为一谈。

- **Q：Skill、MCP、Function Calling、CLI、Runtime 有何区别？Skill 如何按需加载？**

  **A：【部分实现】** MCP 是跨进程能力发现与调用的协议；Tool 是可执行操作；Function Calling 是模型提出“调用哪个工具、传什么参数”的输出机制；Skill 是业务步骤、话术和约束，项目中的 Skill 实际是热加载的提示词文本；CLI 是交互入口或工具的另一种封装；Runtime 负责 Agent 主循环、上下文、状态、权限和错误处理。项目按 Agent 类型和关键词只注入命中的 Skill，并限制总字符数。真正的渐进式披露应进一步做成“先给名称与描述，模型确认需要后再读取完整正文”，当前只实现了初级筛选。

- **Q：Skill、MCP、TOOLS 分别是什么，各自解决哪一层问题？**

  **A：【已实现】** Skill 解决“怎么做、遵守什么业务规则”，项目里对应 Markdown 规则；Tool 解决“能做什么”，例如查知识库、查错误码；MCP 解决“不同进程或系统怎样标准化发现和调用 Tool/Resource”。三者不是替代关系：MCP 可以承载 Tool，Tool 可以被 Function Calling 触发，Skill 影响模型选择和编排 Tool 的方式。

- **Q：什么是 Skill？Skill 和普通 Function Call 之间的核心区别是什么？**

  **A：【已实现】** Skill 是可维护的流程知识，通常不直接产生外部副作用；Function Call 是结构化执行请求，最终会进入某个 handler。项目中的 Billing Skill 规定收款字段和退款话术，而 `check_billing_fields` 才是实际执行的函数。Skill 可在不修改程序的情况下热加载，Function Call 的权限、Schema 和执行逻辑必须由代码控制。

- **Q：Function Calling 和 MCP 有什么区别？**

  **A：【已实现】** Function Calling 是模型层机制，模型输出工具名和参数；MCP 是系统之间的协议层，定义工具发现、资源读取、调用和传输。Function Calling 可以直接调用本地函数，也可以调用 MCP 暴露的远端工具。MCP 不会替代模型规划，也不保证参数一定安全。

- **Q：Tool Calling VS MCP，什么时候用哪个？**

  **A：【已实现】** 同进程、稳定、少量私有能力直接注册本地 Tool 更简单；需要被多个客户端复用、跨语言、跨进程、独立部署时使用 MCP。项目把本地知识库做成 MCP 服务供外部客户端使用，同时把本地角色工具保留为进程内 Tool。

- **Q：MCP 有什么优势？你们为什么做 MCP？**

  **A：【已实现】** 优势是标准发现、统一 Schema、跨进程复用、语言无关和客户端可插拔。项目使用 MCP 一方面接入外部公开文档服务，另一方面把本地知识库开放给其他 MCP 客户端，避免每个调用方都重复实现知识查询接口。

- **Q：为什么需要 MCP？MCP 主要解决什么场景和问题？**

  **A：【已实现】** 主要解决 Agent 与外部能力之间的 N×M 集成问题：客户端不必为每个工具写一套私有适配，工具提供方也只实现一次协议。适合多工具、多模型、多运行时的平台化场景。对于只有两三个本地函数的小系统，直接 Function Calling 即可，MCP 可能增加部署和权限复杂度。

- **Q：你怎么理解 Skill？为什么会出现 Skill？它主要解决什么场景？**

  **A：【已实现】** Skill 的出现是为了把易变的业务 SOP 从代码和超长系统提示词中拆出来，降低运营维护成本和提示词污染。它适合更新频繁、跨角色有差异、但又不需要执行代码的规则，例如退款流程、升级条件、回复边界。

- **Q：你怎么理解 Skill？Skill 的设计主要为了解决什么问题，有哪些优势？**

  **A：【已实现】** 核心是把“知识、流程、约束”产品化，做到按需加载、版本管理和热更新。优势是可维护、可复用、可审计、上下文占用少。局限是它仍然是自然语言约束，不能替代服务端鉴权和工具参数校验。

- **Q：Skill 设计出来的初衷是什么？**

  **A：【部分实现】** 初衷是让 Agent 不把所有业务规则永久塞进系统提示词，而是根据当前角色和任务加载需要的规范。EchoMind 用这个思路拆出了通用客服、技术支持、账单处理三类 Skill。

### 1.2 MCP 工程细节

- **Q：MCP 在 Agent 的生命周期中什么时候加载、发现并注册工具？**

  **A：【已实现】** Java 版在应用启动后连接 MCP Server，完成 initialize 和分页 `listTools`，再按服务白名单、Agent 范围、只读声明过滤并注册到 `ToolRegistry`；之后周期重连，并在工具列表变化时刷新注册表。Python 版同样在启动阶段发现外部工具，配置变化或应用重启后重新装配角色工具。

- **Q：内部接口封装成 MCP 时，Schema 怎么设计？错误信息怎么给模型？要不要支持流式返回？**

  **A：【已实现】** Schema 只暴露完成任务必需的字段，明确 `required`、类型、范围、枚举和额外字段策略；用户、租户、权限不从模型参数读取，而由服务端上下文注入。错误分成参数错误、权限错误、可重试网络错误、业务拒绝和未知副作用结果。短查询不需要流式；长任务应返回任务 ID 并通过进度通知或轮询暴露状态，当前项目没有实现业务流式 MCP。

- **Q：MCP Server 需要考虑哪些安全问题？**

  **A：【部分实现】** 项目已有 HTTPS URL 校验、工具白名单、Agent 白名单、只读声明过滤、stdio 环境变量白名单、超时、结果大小限制和 Token 鉴权。完整方案还需要 OAuth/短期凭证、租户隔离、工具级 RBAC、SSRF 防护、命令执行沙箱、限流、审计、密钥托管，以及对工具返回内容做“不可信数据”隔离。

- **Q：MCP 开放给个人 Agent 时，权限怎么校验？**

  **A：【部分实现】** 项目当前主要使用 API Bearer Token 和服务端用户身份，尚未实现面向第三方 Agent 的 OAuth Scope 体系。通用做法是使用 OIDC/OAuth2 的短期 access token，绑定用户、租户和 scope；MCP Server 对每次调用同时校验调用方、目标用户、资源范围和工具权限，高风险写操作要求二次确认。

- **Q：MCP 是开放层还是只服务于你们自己的软件？**

  **A：【已实现】** 协议层是开放的。EchoMind 的 `/mcp/` 可供其他标准 MCP 客户端访问，但当前实际开放能力主要是本地知识检索与知识统计，不是完整的客服业务系统，也不代表订单、退款等写能力已对外开放。

- **Q：MCP 工具调用失败后，怎么保证用户知道任务的最终状态？**

  **A：【部分实现】** 工具错误会回传给模型，Agent 必须明确说明未完成、原因和下一步。对于 `retry_safe=false` 的写工具，调用前先写入 `tool_outcome_unknown` 回执，失败后不自动重放。通用方案还需要业务侧提供 `operation_id` 和结果查询接口，才能区分“未执行、执行中、成功、失败、结果未知”。

### 1.3 Skill 加载与路由

- **Q：Skill 后续会不断增加、更换，除了写在 System Prompt 里，还有什么方式让模型正确找到并使用？**

  **A：【部分实现】** EchoMind 先按 Agent 类型过滤，再按关键词匹配，最后受字符预算限制。规模变大后应使用两层路由：先用 Skill 名称、描述和标签做 BM25/向量召回，选 Top-K；再读取候选 Skill 正文，必要时提供 `load_skill(name)` 工具实现渐进式披露。

- **Q：怎样让大模型更好地识别用户意图，并正确触发对应的 Skill？**

  **A：【部分实现】** 项目的意图识别和 Skill 匹配是两套规则：三路意图识别负责业务路由，关键词与 Agent 类型负责 Skill 选择。可改进为让 Skill 元数据进入意图候选，或使用“用户意图—Skill 描述”的交叉编码重排，再加入负样本和触发/不触发评测。

- **Q：Skill Register 动态加载业务 Skill 的过程是怎样的，怎么做到动态加载？**

  **A：【部分实现】** 当前不是完整 Skill Registry，而是目录扫描：应用读取 `SKILL.md`/JSON/TXT，解析元数据和正文，通过 `/skills/reload` 全量重扫。严格动态加载应增加注册、注销、版本、依赖、校验和按需读取接口，并在新版本通过评测后再切换流量。

- **Q：Skill 的渐进式披露是什么含义？这个机制为什么可以提升 Agent 运行稳定性？**

  **A：【部分实现】** 渐进式披露是只先给模型 Skill 的名称、描述和触发条件，确认相关后再加载完整步骤或脚本。它减少无关上下文、降低提示冲突和 token 成本。项目只做到按关键词筛掉无关 Skill，未实现第二阶段按需读取全文。

- **Q：如果接入你的编程助手，Skill 要怎么装载？**

  **A：【项目未涉及】** 通用方案是启动时发现本地 `.agent/skills` 目录，索引 `name/description/triggers`；每轮按任务检索 Top-K，先注入摘要；模型需要时读取完整 `SKILL.md`；Skill 中声明的脚本只能从白名单目录执行，并受权限、沙箱和审批控制。

### 1.4 工具选择与调度

- **Q：工具很多时（20+），如何稳定选对？工具描述怎么优化？工具怎么检索和动态加载？**

  **A：【项目未涉及】** 项目只有少量角色工具和外部工具白名单，没有面对 20+ 工具。通用方案是先做两级候选缩减：用领域/意图和权限过滤，再用工具描述、示例、参数名做 BM25/向量召回，重排到 5～10 个；工具名使用稳定命名空间，描述写“何时用、何时不用、返回什么”，并用难负样本评测误选率。

- **Q：我们工具不多，问一次调用是否要全部传给 LLM？**

  **A：【已实现】** 项目会把当前 Agent 有权限使用的工具全部传入该 Agent 的模型请求。工具少时这样做简单且准确；数量增多后应只传候选工具，否则 Schema 占 token、增加混淆并扩大误调用面。

- **Q：多个工具同时触发，怎么不乱？**

  **A：【部分实现】** 项目会逐个处理模型同一响应中的多个 `tool_use` 块，工具轨迹带调用 ID 和 Agent 类型，避免结果串线。更高并发时应按依赖图调度：无依赖只读工具并行，有依赖工具按拓扑顺序，写操作按资源键串行，并对同一请求的重复调用去重。

- **Q：如果模型选错工具了，系统怎么兜底？**

  **A：【已实现】** 首先由 Agent 工具白名单和 JSON Schema 在 handler 前拦截；工具失败后将结构化错误交回模型继续推理；专业 Agent 整体失败时回退 General。若已尝试副作用工具，则不自动交给另一个 Agent 重做。更成熟的方案还要增加工具级候选重排和误选评测。

- **Q：你们一共做了哪些工具？介绍一下工具设计。**

  **A：【已实现】** 项目有请求上下文检查、补充字段建议、错误码解释、排障计划、账单字段检查、金额差值计算、知识库检索、人工交接摘要等角色工具，以及 Microsoft Learn 外部 MCP 工具。统一设计包含名称、描述、JSON Schema、角色范围、超时、缓存、只读/副作用声明、handler 和调用轨迹。

### 1.5 工具调用异常

- **Q：Function Calling 的完整链路是什么？参数错误、超时、异常分别怎么校验、重试、降级？**

  **A：【已实现】** 链路是模型输出 `tool_use` → 角色白名单检查 → JSON Schema 校验 → 副作用前置保护 → 执行 handler → 返回 `tool_result` → 模型继续生成。参数错误直接回传，不重试；瞬时网络超时只对幂等工具做有限重试；持续失败触发缓存降级或熔断；副作用结果未知时停止自动重放并要求核验。

- **Q：工具调用返回脏数据或超时，Agent 怎么兜底，不让它继续乱执行？**

  **A：【已实现】** 工具层校验返回结构并限制大小；超时、异常和熔断会返回明确失败，知识库失败不会被当成成功证据。模型可给用户解释并继续安全步骤，但已尝试写操作时不再自动兜底执行。还应增加字段级校验、来源可信度、内容净化和最大循环数。

- **Q：工具调用超时或返回异常后，是直接终止还是继续让 Agent 重试？**

  **A：【已实现】** 取决于工具幂等性和剩余预算。只读且可重试的工具可以有限重试；非幂等工具不能盲目重试；连续失败进入熔断；超过 Agent 或整轮预算直接失败或部分成功。EchoMind 将“可重试”显式建模为 `retry_safe`，并对写操作记录结果未知。

- **Q：Agent 线上运行时，Skill 调用失败、超时，设计什么样的降级重试策略？**

  **A：【部分实现】** 项目 Skill 本身是本地文本，不存在远程超时；相关工具才有超时、缓存和熔断。可借鉴同样策略：Skill 读取失败使用已缓存版本，新版本失败回退旧版本，工具失败只在幂等条件下重试，并记录版本、错误和降级来源。

- **Q：Function Calling 完整流程中，参数异常如何处理？**

  **A：【已实现】** 项目在执行前检查必需字段、类型、数值范围、枚举和额外字段，错误以工具结果返回模型。不会用默认值悄悄补齐关键字段；可推导的默认值也要在 Schema 和 trace 中体现。业务权限必须在 handler 内再次校验。

- **Q：模型输出结构化参数失败（JSON 解析异常）怎么处理？**

  **A：【部分实现】** 工具参数由模型协议返回，不直接信任文本 JSON；内部摘要、画像和 Judge 的 JSON 若解析失败，会保留原状态或记录评分失败。通用恢复是首选结构化输出/严格 Schema，其次进行一次带错误原因的格式修复，最后降级为追问或确定性路径，禁止无限“修 JSON”循环。

- **Q：模型输出结构化 JSON，你怎么设计数据结构、错误恢复机制？格式异常、字段缺失怎么处理？**

  **A：【已实现】** 项目使用数据类/DTO 和 JSON Schema 约束关键字段，解析后检查类型、范围、额外字段。缺字段时区分“可安全再问一次”和“必须失败”；Judge 缺字段记为评分不可用，不伪造 0.5 分。设计上应保留原始输出、解析错误、尝试次数和最终状态。

- **Q：重试策略怎么设计？**

  **A：【已实现】** 按错误分类、幂等性、预算和退避设计。4xx 参数/鉴权错误不重试；408/429/5xx 或网络错误可指数退避加抖动；模型调用有单次超时和整轮预算；Judge 最多两次；工具连续失败熔断；请求级重试由 `client_request_id` 去重；写操作依赖业务幂等键和结果查询。

### 1.6 Spring / 后端工具层

- **Q：Spring 里怎么设计一个 Agent 工具调用层？工具元信息怎么注册和管理？**

  **A：【已实现】** Java 版通过 `ToolDefinition` 管理名称、描述、JSON Schema、Agent 范围、只读标志、超时、缓存 TTL、来源和 handler，由 `ToolRegistry` 统一注册、过滤、校验和统计；LangChain4j 的 ToolProvider/Executor 负责模型调用桥接，角色只能在授权范围内看到工具。

- **Q：Agent 能力如何接入 Spring 微服务？**

  **A：【部分实现】** 项目 Java 版把模型调用、工具注册、会话、鉴权和监控作为 Spring Bean 接入。对接真实微服务时，推荐两种方式：同一平台内通过内部 RPC/HTTP 适配成 Tool；跨团队或跨技术栈则封装成 MCP Server。两种方式都要保留服务端鉴权、超时、熔断、幂等和审计。

## 二、记忆层

### 2.1 记忆分层

- **Q：长短期记忆如何存储、更新和遗忘？**

  **A：【已实现】** 近期消息、会话摘要和当前业务字段存 Redis，工作消息默认保留 24 小时；超过阈值后后台摘要，情景记忆和用户画像存 ChromaDB。遗忘通过 TTL、消息裁剪、旧摘要合并和用户级覆盖实现。当前没有完整的人工“删除某条长期记忆”接口。

- **Q：长期记忆、短期记忆分别用什么形式存储？**

  **A：【已实现】** 短期是 Redis 列表加摘要；结构化任务字段是 Redis JSON；长期是 ChromaDB 中的摘要型情景记忆和按用户聚合的画像文档。代码和制度知识另存知识库 collection，不能与用户记忆混为一谈。

- **Q：讲一下分层记忆和记忆自进化的设计。**

  **A：【部分实现】** EchoMind 的分层是工作记忆、摘要、情景记忆、画像和结构化业务状态。自进化只做到后台用 LLM 从最近对话中提炼偏好与实体并更新画像，不是持续训练模型；也没有自动验证新记忆是否正确的闭环。

- **Q：记忆模块怎么做的？压缩会不会丢信息？怎么评估信息留存和丢失情况？**

  **A：【部分实现】** 压缩会丢细节，项目通过保留最近 5 条消息、独立业务字段、摘要中的偏好/实体/待办/约束/未解决问题来降低损失。当前没有专门的记忆留存率指标；应构造“先给事实，压缩后再问”的测试集，评估精确召回、冲突处理和无关信息率。

- **Q：讲一下你们的记忆管理策略、滑动窗口剪切逻辑。**

  **A：【已实现】** Redis 原始顺序为最新在前；读取最多 20 条并恢复时间顺序。达到 15 条后触发后台压缩，对旧消息摘要，快照保留最近 5 条；压缩期间新增消息也会保留。Agent 实际背景最多使用最近 8 条和 3 条相关历史。

- **Q：有没有做用户长期记忆优化？**

  **A：【部分实现】** 有用户画像和跨会话情景检索，会去重并限制长度，但主要是“提炼并存起来”，尚无独立长期记忆评测、纠错界面和遗忘策略自动优化。

### 2.2 压缩与归档时机

- **Q：归档算不算记忆压缩？归档的落盘时机是什么——每次工具调用完，还是整个会话结束？**

  **A：【已实现】** 归档是压缩后的持久化形式，把旧对话摘要写入 ChromaDB。HTTP 主链路是在整轮成功/部分成功后先提交 Redis，再把压缩和归档交给后台队列；不在每次工具调用后归档，避免破坏单轮一致性。

- **Q：短期记忆有没有落盘或压缩机制？**

  **A：【已实现】** 有。Redis 本身持久化近期消息；达到阈值后生成摘要，合并旧摘要并裁剪消息，随后写情景记忆。摘要为空或被截断时保留原历史，不执行危险裁剪。

- **Q：历史对话怎么摘要压缩？**

  **A：【已实现】** 先从完整快照中取出除最近 5 条以外的旧消息，用 LLM 生成摘要，再把旧摘要与新摘要合并到最多 800 字符。提交前用 `WATCH/MULTI` 校验快照和旧摘要未变化，防止覆盖并发新增消息。

- **Q：长期记忆怎么更新，覆盖还是冗余存储？**

  **A：【部分实现】** 用户画像按用户 ID 覆盖更新；情景记忆按会话摘要追加，属于冗余事件型存储。更好的做法是“事实 upsert、事件 append、冲突保留来源和时间”，并在读取时按可信度与时间做合并。

### 2.3 召回与检索

- **Q：记忆怎么召回？为什么不用向量数据库？**

  **A：【已实现】** 项目实际上同时用了键值存储和向量库。近期上下文和当前字段按用户、会话精确读取，因为需要低延迟和强一致；长期情景摘要与画像使用向量语义召回。不能把所有记忆都塞进向量库，因为当前任务字段必须精确、可更新、可追踪来源。

- **Q：长期知识是怎么设计的？记忆模块的效果提升是怎么评测出来的？**

  **A：【部分实现】** 长期知识分为知识库、情景记忆和用户画像。项目提供了对话评测和逐请求 trace，但没有单独的 memory benchmark；应增加多会话事实延续、冲突更新、无关噪声、遗忘和跨用户隔离测试，再报告留存率与错误率。

### 2.4 冲突与跨会话

- **Q：历史记忆与当前会话冲突怎么办？**

  **A：【已实现】** 当前用户明确表达优先于旧记忆；结构化状态检测订单变化、新任务和业务域变化后清理旧字段，并记录字段来源 `request_id`。旧聊天不会被删除，但工具必须使用当前结构化字段和业务系统核验结果。

- **Q：大量历史、长期记忆和用户新设定冲突、上下文放不下时，删减/保留策略怎么定？怎么避免旧记忆覆盖新要求？**

  **A：【已实现】** 保留优先级是安全/合规约束、当前任务目标与字段、最近消息、新摘要、相关长期记忆、一般旧偏好。EchoMind 将当前实体独立于摘要保存，并在换任务时重置；通用系统还应给偏好加时间、来源、置信度，冲突时显式询问或采用较新且可信的证据。

- **Q：支持跨会话的记忆吗？**

  **A：【已实现】** 支持。先检索当前用户当前会话，数量不足再查同一用户其他会话，并做去重；不同用户不会互查。结构化订单字段和当前摘要仍按会话隔离。

- **Q：怎么提取用户长期的写作/表达习惯？如何避免把临时、偶然的噪声误识别成固定偏好？**

  **A：【部分实现】** 项目会从最近对话与已有画像中提炼偏好和关键实体。避免噪声需要多次出现证据、时间衰减、置信度阈值、显式确认和可撤销；临时要求应标记为“本次约束”，只有跨会话稳定重复的才升级为长期偏好。

### 2.5 对标产品

- **Q：了解其他框架或产品（如 Claude Code）的记忆是怎么做的吗？**

  **A：【项目未涉及】** EchoMind 没有复刻 Claude Code。公开产品层面的核心思路是项目/用户级指令文件、当前会话工作上下文、自动压缩和工具产生的外部文件状态共同协作。面试时应避免声称掌握未验证的内部实现。

- **Q：有了解 Claude Code 的记忆机制吗？是分层记忆吗？**

  **A：【项目未涉及】** 可以概括为“持久指令 + 会话上下文 + 压缩/摘要 + 文件系统状态”，但具体分层和内部阈值不应臆测。EchoMind 自己的边界是 Redis 短期状态、摘要、ChromaDB 长期记忆和业务结构化字段。

### 2.6 效果验证

- **Q：记忆模块完成率已经到 70%，想提到 90% 有什么方案？**

  **A：【项目未涉及】** 先定义完成率是事实召回、任务延续还是冲突处理，并按失败类型分层。重点优化记忆抽取 Schema、保留优先级、跨会话过滤、冲突判定、摘要质量、向量召回与 rerank；再建立回归集、按用户隔离和人工抽检，不能只靠扩大窗口。

- **Q：剩下 30% 的失败分析过吗？主要原因是什么？**

  **A：【项目未涉及】** 项目没有 70% 这个实测数字，不能编造原因。通用归因包括未提取、提取错误、召回失败、排序错误、冲突覆盖、摘要丢失、作用域污染和上下文预算不足，应通过逐阶段 trace 和标注集定位。

## 三、上下文工程

### 3.1 压缩策略

- **Q：上下文何时压缩、保留什么？如何检查信息丢失？**

  **A：【已实现】** HTTP 对话在消息达到 15 条后由后台压缩；保留最近 5 条完整消息，并单独保留订单号、金额、日期等结构化状态。摘要提示明确保留用户偏好、关键实体、待办、约束和未解决问题。项目通过保留原始状态、最近消息和失败不裁剪来降低丢失，但没有自动计算“信息留存率”，需要专门测试集验证。

- **Q：上下文压缩会不会破坏 Agent 的执行？**

  **A：【部分实现】** 会，如果摘要遗漏目标、工具结果或约束，Agent 可能重复动作或偏离任务。EchoMind 避免把当前任务只放在摘要里：当前字段存入独立 state，最近消息保留原文，摘要失败则保留历史。更稳妥的方案是把目标、禁止事项、已完成步骤和待验证结果设为 pin，不允许摘要器删除。

- **Q：压缩时怎么判断哪些信息需要保留？**

  **A：【已实现】** 规则上保留当前任务、业务实体、用户偏好、约束、待办和未解决问题；实现上最近 5 条不压缩，结构化字段不进摘要。通用排序可采用：安全约束 > 当前目标 > 未完成动作 > 工具证据 > 用户偏好 > 普通闲聊。

- **Q：了解主流产品的上下文压缩机制吗？你的方案和它们有什么区别？**

  **A：【部分实现】** 主流思路通常是“保留最近上下文 + 摘要旧上下文 + 将大材料外置 + 按需重新读取”。EchoMind 的差异是额外保存可精确合并的业务 state 和字段来源，减少订单号、金额这类事实依赖自然语言摘要。但没有代码级复刻任何特定产品，不能声称与其内部机制一致。

- **Q：上下文压缩策略是什么？**

  **A：【已实现】** 先提交本轮结果，再异步压缩；对旧消息摘要，合并旧摘要，最多 800 字符，保留最近 5 条；压缩期间新增的消息也保留。Agent 侧只注入最近 8 条、3 条相关历史、画像、摘要和结构化字段，避免把所有历史原文重复送入模型。

- **Q：上下文压缩怎么保证任务目标不偏移？**

  **A：【部分实现】** 当前通过角色输入契约、结构化意图、实体和最近消息保持目标。为了防止偏移，应把原始任务目标、成功条件和禁止操作作为不可摘要字段；每轮由程序检查当前动作是否仍服务于目标；完成结果由 verifier 或确定性检查确认。

- **Q：业务落地中怎么做上下文压缩？如何平衡 Token 开销和模型决策效果？**

  **A：【已实现】** 项目用分层装配控制成本：短期原文、摘要、相关长期记忆、画像、业务字段和 Skill 各有预算；无关 Skill 不注入，RAG 只按需调用。平衡点是先保证关键状态原文无损，再压缩叙述性历史；用离线评测比较不同预算下的成功率、延迟和费用。

- **Q：上下文过长如何压缩、截断、摘要？**

  **A：【已实现】** 项目优先摘要并保留最近消息；Java 在 token 预算不足时按完整对话轮次删除旧消息，不截断当前问题，也不拆散 tool call/result。工具结果超限时转为带 `truncated=true` 的合法 JSON。通用顺序应是先外置、再检索、再摘要、再按轮次删除，最后才截断非关键文本。

- **Q：大资产场景下的上下文装配，上下文膨胀怎么处理？**

  **A：【部分实现】** 项目限制 Skill、背景、工具结果和知识 Top-K，并将大工具结果外置为截断标记。大资产系统应使用对象存储保存原文，上下文只放文件清单、索引、摘要和引用；Agent 通过分段读取、grep/检索、代码符号导航按需加载。

### 3.2 超长输入

- **Q：单个开发大任务长度就超过上下文限制怎么办？**

  **A：【项目未涉及】** 通用方案是将任务拆成有依赖的里程碑，保存可恢复计划、代码索引、diff 和测试结果；每步只读取相关文件和符号，使用 scratchpad/artifact 存长期状态；失败或中断后从持久化 checkpoint 恢复。

- **Q：几百页长文档怎么处理？**

  **A：【已实现】** 文档先切片并向量化，查询时通过知识库检索 Top-K；检索包装器可查询改写、并行召回和重排。更完整的阅读方案还需章节树、页级元数据、逐段摘要、多跳检索和引用定位，项目当前并不是一次性读完整本长文档。

- **Q：长工具调用结果外置了，每次模型不还是只读一点内容吗，怎么读完全部文章？**

  **A：【部分实现】** 项目当前只把有限预览交给模型，超大结果会标记截断，并没有实现自动读完全部文章。正确方式是为大结果提供 artifact ID、分页/区间读取和搜索工具，让模型先定位相关段，再按需迭代读取；同时记录已读游标，防止重复读取。

- **Q：为什么 Agent 不能简单地无限增加上下文？**

  **A：【已实现】** 因为成本、延迟和注意力都会恶化，长上下文还可能带来 lost-in-the-middle、无关信息干扰和安全边界混淆。项目因此采用摘要、分层记忆、工具结果预算和按需 RAG，而不是无限追加。

### 3.3 多轮与 Query 改写

- **Q：多轮对话有哪些缺陷？Query 改写解决什么？Prompt 各部分如何排序？**

  **A：【已实现】** 多轮会有指代省略、话题切换、历史冲突和上下文膨胀；Query 改写把“那个退款呢”补成可检索的完整查询。Prompt 应优先放系统安全与角色边界，再放当前任务/结构化状态、任务目标、必要历史和工具资料，最后放用户原文；低可信工具内容要明确标记为资料而不是指令。

- **Q：Query Rewrite 解决什么问题，如何验证改写效果？**

  **A：【已实现】** 它解决省略、口语化、单角度表达导致的召回不足。项目保留原始查询，再增加最多 3 个改写查询并行召回。验证要比较开启/关闭改写后的 Recall@K、MRR、nDCG、最终答案质量和延迟；不能仅凭一段看起来更完整的改写文本判断有效。

- **Q：用户 Query 进来以后，检索之前有没有做 Query Rewrite？**

  **A：【已实现】** 有，但只在 Agent 决定调用知识库工具后发生，不是每个请求入口都强制改写。原查询始终保留，并生成最多 3 个不同角度的子查询。

- **Q：Query Rewrite 如果把用户原始意图改错了怎么办？**

  **A：【已实现】** Python 和 Java 都会把原查询与改写查询一起保留、并行召回和合并，降低完全偏离的风险。进一步应对订单号、错误码、专有名词等关键实体做保护，校验改写是否改变了数字或否定词，并在融合时给予原查询更高权重。

- **Q：多轮上下文怎么存储、管理会话生命周期？**

  **A：【已实现】** Redis 以用户和会话生成哈希键保存近期消息、摘要和状态，默认 24 小时；ChromaDB 保存压缩后的情景摘要和用户画像。回执保留 24 小时，聊天轨迹 7 天，最近轨迹最多 200 条。

- **Q：已经进行了很多轮对话，中途从模型 A 切换到模型 B，怎么保证上下文和任务还能继续？**

  **A：【部分实现】** Java 版通过 LangChain4j 和统一消息模型降低了适配成本，Python 使用 Anthropic Messages 兼容接口。项目支持按角色配置模型，但没有同会话热切换后的自动迁移测试。通用方案是使用厂商无关的 message/tool/state Schema，任务状态和摘要独立于模型，切换后重新计算 token 预算并跑兼容性评测。

### 3.4 参数与成本

- **Q：32 轮对话窗口这个数字是怎么定出来的？**

  **A：【项目未涉及】** EchoMind 没有 32 轮窗口，实际是从 Redis 最多读 20 条近期消息，Agent 背景最多用最近 8 条，最多再取 3 条相关历史。面试时不能说 32 轮来自本项目；参数应通过上下文长度、任务完成率和 P95 延迟的实验确定。

- **Q：主 Agent 最多 30 轮迭代、超时 300 秒，是主观定的吗？系统做出来后有让同学试用过吗？**

  **A：【项目未涉及】** 项目没有 30 轮 / 300 秒设定。Python 每个 Agent 最多 3 轮模型请求，Java 最多 4 轮工具执行，聊天总预算为 50 秒；这些是为了控制延迟和死循环的工程上限，仓库中没有真实用户试用统计。

- **Q：一次会话消耗多少 Token？如何提高缓存命中率、做模型路由及超限处理？**

  **A：【部分实现】** Java 默认输入预算 48,000 估算单位，背景 4,000，单工具结果 2,000，并记录模型 token usage；Python 通过消息条数、Skill 字符数和工具限制控制。项目没有 LLM Prompt Cache 命中率数据。通用优化包括稳定前缀、缓存断点、重复工具结果 TTL、意图/工具缓存、按复杂度路由小模型和预算分级。

- **Q：电商项目里的 Cache Breakpoint 思路是什么？命中率稳定在 80% 是怎么做到的？**

  **A：【项目未涉及】** EchoMind 没有 80% Cache Breakpoint 指标。Prompt Cache 的通用做法是把稳定系统提示、工具 Schema 和长期规则放前缀，把变化内容放后缀，并在供应商支持的位置设置缓存断点；命中率需由服务商 usage 字段和生产监控证明，不能凭设计目标宣称。

## 四、Agent Loop / 规划与决策

### 4.1 循环本身

- **Q：完整描述 Agent ReAct 循环。**

  **A：【部分实现】** EchoMind 实现的是有界 ReAct-like Tool Loop：观察用户问题与背景 → 模型选择直接回答或输出 tool call → 程序校验并执行工具 → 把 observation 以 `tool_result` 返回 → 模型继续推理。最多 Python 3 轮、Java 4 轮，没有单独持久化 Thought 字段，也不公开模型内部思维链。

- **Q：Agent Loop 怎么写的？**

  **A：【已实现】** 外层先做鉴权、锁、回执和上下文；内层构造 system、背景、实体和用户消息，循环检查模型响应中的 `tool_use`。没有工具调用就得到最终答案；有工具就执行并将结果追加到消息；达到上限则失败。多余工具调用有单轮上限，工具或模型单次调用还有超时。

- **Q：Agent Loop 一般什么时候结束？**

  **A：【已实现】** 模型返回无工具调用的最终文本、发生不可恢复错误、超过工具/模型轮数、超过整轮超时、输出为空或被判定为 partial/failed 时结束。

- **Q：Agent 什么时候停止循环？**

  **A：【已实现】** 与上一题相同，主要由“没有下一步工具请求”或预算耗尽触发。项目不会因为模型说一句“完成了”就绕过外层状态检查，但 Python 版也没有独立的业务完成证明器。

- **Q：Agent 怎么知道是否完成任务？**

  **A：【部分实现】** Python 版通过最终文本非空、是否截断、工具成功状态和执行状态判断；Java 版另有 `AnswerVerifier` 检查 `pass` 和 `grounded`。真正的任务完成应由 schema、数据库状态或外部结果查询确定，例如退款必须查到业务单状态，不能只信自然语言声明。

- **Q：模型说自己“任务完成了”，系统就直接相信吗？还是会做结果校验？**

  **A：【部分实现】** 不应完全相信。EchoMind Java 版在交付前调用回答校验器，拒绝不合格答案并转人工；工具有 `success` 与 `result_success` 区分。但当前没有真实订单/退款系统，因此无法证明所有业务动作完成；生产方案必须增加确定性结果查询。

- **Q：无人值守时，如何验证任务真正完成？**

  **A：【部分实现】** 应由程序和外部系统验证，而不是让模型自证。每步定义完成条件、证据和副作用状态；工具返回业务单号后查询最终状态；失败进入重试、补偿或人工队列。项目已有状态、回执、trace 和验证器框架，但真实无人值守业务闭环未实现。

- **Q：怎么做的约束？**

  **A：【已实现】** 约束包括角色工具白名单、JSON Schema、Agent 范围、只读 MCP 声明、总时长、模型轮数、工具调用次数、结果大小、允许的 Agent 类型、副作用前置回执和查询范围限制。

- **Q：分享一个 Agent 死循环、错误归因的失败案例，你怎么定位？Harness 加了哪些限制防止死循环？**

  **A：【部分实现】** 项目没有可引用的真实线上死循环案例，不应编造。代码层面通过最大轮数、总超时、工具调用上限、相同副作用参数去重、熔断和循环检测（Java AgentBus）防住常见情况；定位时比较相邻 tool call 的“工具名+规范化参数”、状态差异、错误码和剩余预算，若签名不变且状态不变就判重复循环。

- **Q：如果 Agent 一直重复调用同一个工具，怎么判断它进入死循环？**

  **A：【部分实现】** 可对工具名和规范化参数生成签名，如果连续 N 次签名相同且 observation/任务状态未变化，就判定无进展；再结合轮数、时间、总 token 和相同错误重复次数。EchoMind 已阻止同一请求重复执行相同副作用工具，Java AgentBus 有访问栈循环检测，但对普通只读工具尚无完整“无进展”检测器。

- **Q：你们的 agent 循环、多轮调用、agent 核心模块是什么？**

  **A：【已实现】** 核心是 Agent Profiles、Tool Registry、有界 Tool Loop、Orchestrator、Response Composer、Memory、Monitor、Trace 和 Evaluator。Python 本地执行多 Agent 主辅路由；Java 由 LangChain4j AiServices 负责模型与工具消息循环，应用层继续负责会话锁、状态和最终提交。

### 4.2 范式选型

- **Q：为什么用 Agent 而非固定 Workflow？哪些决策交给模型，哪些由代码控制？**

  **A：【已实现】** EchoMind 实际是混合架构：鉴权、锁、意图路由、工具白名单、预算和存储由代码控制；模型只在授权工具集合内决定是否检索、选择哪个安全工具以及如何组织回答。这样保留一定自主性，又避免让模型决定权限和高风险写操作。

- **Q：ReAct 和 Workflow 对比，OTA 场景怎么选？**

  **A：【项目未涉及】** 固定流程如查单→验价→锁库存→支付应使用可恢复 Workflow；用户需求开放、信息不足、需要多轮检索或排障时使用受限 ReAct。OTA 场景适合“Workflow 骨架 + 局部 Agent”的混合模式，支付、取消和改签等关键节点必须用确定性规则和人工确认。

- **Q：ReAct 和 Plan-Execute 两种 Agent 范式，分别适合什么业务？**

  **A：【部分实现】** ReAct 适合步骤短、依赖观察动态调整的排障和检索；Plan-Execute 适合步骤多、可预先拆解、需要并行和 checkpoint 的长任务。EchoMind 没有显式 Plan Agent，采用稳定路由 + 局部 ReAct，因此长复杂任务不是当前强项。

- **Q：开发 Agent 的三种范式。**

  **A：【项目未涉及】** 常见划分是固定 Workflow、ReAct 式动态工具循环、Plan-Execute 式先规划后执行；也有 Reflexion/Critic、Graph/多 Agent 编排等扩展。回答时可按三点说清：控制流由谁决定、状态如何持久化、失败如何恢复。

- **Q：Tool vs Agent vs Workflow。**

  **A：【已实现】** Tool 是一个原子能力；Agent 是能根据观察选择下一步的模型驱动执行者；Workflow 是代码定义的确定性步骤和依赖。EchoMind 把权限、状态和存储放在 Workflow/Orchestrator，把局部“是否检索、如何回答”交给 Agent。

- **Q：Agent 和普通对话机器人区别？什么时候适合上 Agent？**

  **A：【已实现】** 普通聊天机器人主要生成文本；Agent 能在工具授权下执行动作、观察结果并继续决策。任务需要外部数据、多步操作、动态分支且结果不能用单次生成完成时适合 Agent；只需 FAQ 或固定表单时用 RAG/Workflow 更便宜稳定。

- **Q：金融场景里 Agent 和普通大模型问答的本质区别是什么？**

  **A：【项目未涉及】** 核心不是“回答更像人”，而是受控执行：身份、授权、交易事实、幂等、审计、可撤销和合规边界。模型只能提出动作，金额、账户权限和执行结果必须由金融后端核验，高风险操作必须人工确认。

- **Q：简单任务为什么不能直接用 ReAct 完成？**

  **A：【已实现】** 可以用，但通常不划算。一个明确的 401 查询直接路由到 Technical 并调用错误码工具，比先生成计划再循环更快、更稳定。EchoMind 对简单任务走单 Agent 快路径，对复合领域才并行。

- **Q：如果只是一个非常简单的任务，还重新生成完整 Plan，会不会反而降低效率？**

  **A：【已实现】** 会，因此项目没有对所有请求生成 Plan。先用规则和意图选择快路径，只有需要多步工具时才进入有限工具循环。

- **Q：是不是所有任务都会先经过 Plan Agent？**

  **A：【已实现】** 不是，EchoMind 没有 Plan Agent。所有请求先经过鉴权、会话读取和意图/路由，但只有 Agent 执行阶段可能在授权工具集合内动态选择下一步。

- **Q：Planning 怎么实现？**

  **A：【项目未涉及】** 可让 Planner 输出结构化 DAG：节点、依赖、输入输出、成功条件、风险和补偿动作；Executor 按拓扑执行，每个节点有预算和 checkpoint；Critic 校验结果，Planner 只在失败时重规划。EchoMind 没有这套通用规划器。

### 4.3 意图与路由

- **Q：意图识别具体是怎么做的？**

  **A：【已实现】** LLM 语义识别与在线/本地 Embedding 并行，Pattern 在本地执行，按 0.7/0.2/0.1 融合。先汇总业务组分数，再选组内细意图；低置信度返回 `other` 并可能触发澄清。实体和紧急度使用规则提取。

- **Q：主 Agent 的意图识别有哪些实现方案？为什么单纯依靠单轮分类器效果往往不够？**

  **A：【已实现】** 项目融合 LLM、Embedding 和 Pattern，并让 LLM 参考最近历史。单轮分类器无法处理“那退款呢”“另一个订单”这类指代、省略和任务切换，也缺少业务字段与紧急度。需要历史、结构化状态和多信号融合。

- **Q：意图识别怎么做？多意图如何拆分排序？**

  **A：【部分实现】** 项目最终输出一个主意图；跨领域复合问题通过关键词和辅助领域评分补充最多一个或几个协作 Agent，没有完整的多意图列表、依赖排序和子任务拆解。完整方案应输出 `[(intent, confidence, priority, dependency)]`，再按显式主诉、风险和依赖做拓扑排序。

- **Q：Agent 路由怎么设计：RAG / 工具调用 / 子 Agent 分流？**

  **A：【已实现】** 先识别意图和实体，再用领域分数选 General/Technical/Billing/Escalation；RAG 和工具不是入口硬分流，而是 Agent 在可调用工具中按需选择。这样可避免“所有退款问题都强制检索”或“所有问候都禁止工具”的硬规则。

- **Q：多个 Agent 时，怎么决定路由到哪个 Agent？路由是规则还是让大模型判断？**

  **A：【已实现】** 主要有规则化评分：意图权重、关键词、实体、General 基础分、Agent 可用性和监控惩罚共同决定，不直接让模型自由指定 Agent。意图里的 LLM 只负责分类，不拥有最终路由控制权。

- **Q：用户 Query 进来以后，最先进入哪个 Agent？最后哪个 Agent 负责把结果返回给用户？**

  **A：【已实现】** 先经过入口和服务层，再由 Orchestrator 路由给主 Agent；复合问题会并行执行主辅 Agent，最后统一由 Response Composer 汇总。单 Agent 成功时直接返回其回答，不额外调用 Composer。

## 五、多 Agent 协作

### 5.1 选型与拆分

- **Q：单 Agent、多 Agent 如何选型？中心式与分布式如何取舍？通信结果怎么校验？**

  **A：【部分实现】** 判断标准是角色是否需要不同工具、权限、上下文和评测，而不是数量越多越好。EchoMind 使用中心式 Orchestrator，按业务领域选择主辅 Agent；Java 额外有请求级 AgentBus 支持 ASK/DELEGATE。通信结果会检查目标是否健康、子任务是否成功、消息预算和循环，但当前没有通用事实一致性仲裁器。

- **Q：Multi-Agent 和 Single-Agent 最大的区别是什么？多 Agent 优势在哪？会带来哪些额外问题？**

  **A：【已实现】** 最大区别是上下文、提示词、工具权限和执行轨迹可以隔离，并有独立角色契约。优势是复合问题可并行、权限更小、单角色更易维护和评测；代价是通信、重复推理、汇总冲突、延迟、成本和状态一致性。

- **Q：为什么不能用一个 Agent + 多个 Skill 来替代 Multi-Agent？**

  **A：【部分实现】** 能替代一部分规则差异，但 Skill 只改变提示词，不能天然隔离工具权限、上下文、执行记录和故障域。EchoMind 的 Technical 与 Billing 有不同工具和字段，且需要并行完成复合问题，因此使用多 Agent。若只是话术不同，一个 Agent 加 Skill 更简单。

- **Q：为什么用多 Agent 而不用一个 Agent？**

  **A：【已实现】** “登录 401 且重复扣款”同时需要排障和账单信息。项目并行执行 Technical 与 Billing，各自只获得必要工具，再由 Composer 合并，减少一个超大提示词同时承担多个业务的风险。

- **Q：每个子 Agent 解决的事情是同一类吗？**

  **A：【已实现】** 当前 General、Technical、Billing 是不同业务域，Escalation 是确定性交接节点；同一个 Technical Agent 主要处理技术排障，不是把任意子任务都交给同类 Agent。

- **Q：主 Agent + sub Agent 的架构是怎么考虑的？为什么选这个架构？**

  **A：【部分实现】** Python 是中心式主辅路由，中心节点负责鉴权和最终汇总，专业 Agent 只处理局部领域；Java AgentBus 允许执行中 ASK、DELEGATE 和 CRITIQUE。该架构便于约束权限和统一交付，但中心节点是复杂度和延迟瓶颈。

- **Q：什么是主 Agent 与子 Agent？两者如何分配模型？为什么不建议全部用同一个大模型？**

  **A：【部分实现】** 主 Agent 决定路由或汇总，子 Agent 完成受限领域任务。EchoMind 允许通过环境变量给 General、Technical、Billing 配置不同模型，但默认可以共用同一个 provider。全部用大模型不是绝对错误，问题在于成本、延迟和过强能力带来的越权面；应按任务难度、工具风险和评测结果分模型。

- **Q：在什么情况下，父 Agent 会发起一个子 Agent 来做一部分事情？**

  **A：【部分实现】** Java AgentBus 在跨领域、多实体或 General 主路由时注入通信工具；主 Agent 可在需要退款政策、排障等子问题时发起 ASK，在确认超出能力时发起 DELEGATE。Python 主辅协作由 Orchestrator 在开始阶段决定，不是子 Agent 自主创建任意任务树。

- **Q：代码开发是子 Agent 负责吗？第一个 Agent 是怎么拆任务的？举个具体例子。**

  **A：【项目未涉及】** EchoMind 不包含代码开发 Agent。通用例子是主 Agent 先建立依赖 DAG：定位失败测试 → 阅读相关模块 → 修改实现 → 补测试 → 运行回归；每个节点可交给专门的检索、编辑或审查 Agent，节点输出用文件 diff、测试结果和退出码校验。

- **Q：子 Agent 提示词怎么写的，怎么做到主 Agent 要的这些事情的？具体怎么做到的？**

  **A：【已实现】** 项目用 `AgentProfile`/`profiles.json` 固定子 Agent 的职责、工作流、输入契约、输出契约、升级条件、工具范围和生成参数；主 Agent 传入结构化 `request`、entities、intent 和上下文。真正的权限不只靠提示词，还由工具注册表过滤和参数校验保证。

- **Q：Planner、Executor、Critic 如何分工？为什么拆分？谁汇总结果、处理冲突？**

  **A：【部分实现】** EchoMind 没有独立 Planner，核心是 Orchestrator+Executor；Java 有 AnswerVerifier 作为校验收敛点，失败时可以 CRITIQUE 后修订一轮。通用分工是 Planner 产生 DAG、Executor 执行节点、Critic 校验证据和结果，Composer/Orchestrator 汇总并给出主次与冲突说明。

- **Q：Plan Agent 和 Execute Agent 分别负责什么？**

  **A：【项目未涉及】** Plan Agent 负责把目标拆成有依赖、完成条件和预算的子任务；Execute Agent 执行单个节点并返回结构化结果。EchoMind 依赖固定路由和工具循环，不负责通用计划生成。

- **Q：路由、管理、执行三层架构怎么设计？瓶颈在哪，如何降本？**

  **A：【部分实现】** 项目把入口/编排、角色管理、Agent 执行和工具执行分层；路由和执行状态在进程内，跨会话用 Redis 锁。瓶颈通常是模型调用和汇总；降本方式是快路径、候选工具缩减、小模型处理简单任务、缓存、并行只读调用和非必要不调用 Composer。

- **Q：审查 Agent 大概是怎么设计的？**

  **A：【部分实现】** Java 版 `AnswerVerifier` 用 LLM 检查回答是否通过、是否有上下文依据、是否需要升级；不合格时转人工，校验服务不可用则返回可重试失败。它适合质量门禁，但不是安全证明，也不能替代业务数据库核验。

### 5.2 上下文隔离与通信

- **Q：Agent 之间有没有做上下文隔离？隔离了又怎么通信？**

  **A：【部分实现】** Python 主辅 Agent 共享同一请求背景和结构化字段，但工具轨迹与角色提示独立；Java ASK 会创建子请求并传递父上下文、历史、实体和问题，再只接收结论或状态。隔离的是角色提示、工具权限和消息图，不是完整安全域。

- **Q：Agent A 能不能直接看到 Agent B 的完整历史上下文？**

  **A：【部分实现】** Python 并行角色共享输入背景，不能看到另一个角色内部的完整工具往返；Java AgentBus 只把 ASK 问题摘要、结论、状态和必要元数据放入共享消息图，不默认复制全部子 Agent 历史。

- **Q：Agent 之间传递的是完整对话，还是结构化的中间结果？**

  **A：【部分实现】** 项目一般传结构化 request 和必要背景，AgentBus 消息只保存问题摘要、结论、violation、轮次和访问栈；并行汇总传各 Agent 最终回答及工具状态。完整对话通常由 Composer 自己整理，不是无差别复制。

- **Q：为什么不直接把所有上下文都塞给每个 Agent？**

  **A：【已实现】** 会造成 token 成本、延迟、注意力干扰、敏感信息扩散和工具误选。每个角色只需要职责相关字段和授权工具，跨域结论才通过结构化消息传递。

- **Q：多 Agent 协作时，怎么避免上下文越来越长？**

  **A：【部分实现】** 项目通过角色独立输入、有限历史、工具结果裁剪、消息摘要和汇总后再输出控制增长；Java AgentBus 限制最多 6 条消息和深度 2。更大系统还应对中间结果做压缩、引用和垃圾回收。

- **Q：Skill 和 Agent 在你这里分别承担什么职责？**

  **A：【已实现】** Agent 有独立角色、工具范围、模型参数和执行状态；Skill 只是可热加载的业务规则，影响提示词但不创建新的执行单元、权限或状态。

### 5.3 并发与一致性

- **Q：多 Agent 如何管理 State 和 Checkpoint？怎样避免竞争，恢复后保证幂等？**

  **A：【部分实现】** 当前 State 是请求级对象和 Redis 会话状态，没有 LangGraph 式逐步 Checkpoint。并行 Agent 主要执行只读工具，不共享可变业务资源；会话用进程锁和 Redis 租约锁串行。恢复只到整轮回执和副作用结果未知保护，不能从中间步骤恢复。

- **Q：多个 Agent 修改同一资源如何避免冲突？任务、进度和失败如何同步？**

  **A：【项目未涉及】** 当前工具默认只读，没有多个 Agent 写同一业务资源。通用方案是数据库乐观锁/行锁、资源级租约和 fencing token；共享任务状态用版本号或事件日志，失败作为显式事件广播，不能依赖内存布尔值。

- **Q：多 Agent 并行领任务时，怎么避免重复领取相同任务？**

  **A：【项目未涉及】** 可使用 Redis `SET NX PX`/队列原子出队，或数据库 `SELECT ... FOR UPDATE SKIP LOCKED` 领取任务，写入 lease 和 worker ID；完成时校验 fencing token，过期 worker 不能提交。

- **Q：如果要用锁来避免并发冲突，你怎么做？四个 Agent 同时修改同一条表记录怎么做到不冲突？**

  **A：【项目未涉及】** 短事务优先用数据库行锁或 `version` 乐观锁；长任务用资源租约和版本令牌，不长期持有数据库锁。写操作携带幂等键，提交时检查版本，冲突后重读并合并；不可合并字段要求人工确认。

- **Q：任务队列支持幂等限流，幂等是怎么做的？**

  **A：【部分实现】** 项目有请求回执、写工具参数去重和评测队列容量限制，但没有通用分布式任务幂等。通用做法是以租户+业务键+步骤生成幂等键，执行前查状态，执行中加租约，成功结果持久化，重复消息直接返回已有结果。

- **Q：用户一次性给出多个诉求时，Agent 做任务拆分要注意哪些问题，怎么避免多个任务之间互相干扰？**

  **A：【部分实现】** EchoMind 能识别技术和账单两个领域并并行，但不会生成完整 DAG。拆分时要注意共享实体、依赖、优先级、风险和写冲突；每个子任务使用独立输入输出、超时和工具轨迹，涉及同一订单的写操作应串行并做版本校验。

- **Q：任务拆分以后是串行执行还是并行执行？**

  **A：【已实现】** 独立只读领域分支并行，例如 Technical 与 Billing；有数据依赖或副作用的步骤应串行。当前项目只做领域级并行，没有通用依赖图调度。

### 5.4 单 Agent 状态机

- **Q：主 Agent + sub Agent：单个 Agent 内部状态机怎么设计，避免语音/文本/工具结果并发输入导致状态混乱？**

  **A：【项目未涉及】** EchoMind 只处理文本和工具结果，没有语音流。通用状态机应为每个会话维护单一事件队列和单调序号，事件类型包括 USER_TEXT、ASR_PARTIAL、ASR_FINAL、TOOL_RESULT、CANCEL；只有当前 run 的合法事件可改变状态，过期事件丢弃，工具结果按 call ID 关联，写操作保持串行。

## 六、RAG 与知识库

### 6.1 全链路

- **Q：你的 RAG 是怎么做检索的？**

  **A：【已实现】** Agent 按需调用 `search_knowledge_base`；工具校验 query/top_k，保留原问题并生成最多 3 个子查询，并行召回、按文档身份和片段去重，结果过多时用 LLM 重排，最后返回 Top-K 片段。Python 底层主要是 Chroma 向量检索，Java 是 BM25 与向量分数融合。

- **Q：项目里的 RAG 从文档进入系统开始完整讲一下。**

  **A：【已实现】** 文档上传/提交 → 校验格式和大小 → 按约 500 字/码点切片 → 计算文档身份、内容版本和片段序号 → 写入 Chroma/语义索引 → 更新已有片段并删除多余旧片段 → 清理检索缓存。查询时执行 rewrite、并行 recall、去重、rerank 和 Top-K 返回。

- **Q：RAG 全链路，各环节踩过哪些坑？**

  **A：【已实现】** 项目重点处理了旧片段残留、同标题不同文档冲突、并发缓存失效后旧结果回填、查询改写失败、重排解析失败、知识工具失败被误当成功证据等问题。仓库没有真实生产事故记录，回答时只能讲这些已测试的设计问题，不能编造线上复盘。

- **Q：向量召回的流程，索引用的是什么？为什么选 HNSW？**

  **A：【部分实现】** Python 使用 ChromaDB 默认向量索引和 all-MiniLM-L6-v2，Java 可切换 LangChain4j 的本地/Chroma 语义存储。Chroma 内部通常采用 HNSW 类近似近邻索引，但项目没有做 HNSW 参数消融，因此不能声称“经过实验证明优于其他索引”。选择它主要是开发集成和本地部署成本低。

- **Q：了解哪些检索实现方式？**

  **A：【已实现】** 项目使用 Dense Retrieval，Java 额外实现 BM25 词法检索、查询改写和 LLM rerank。常见方案还包括稀疏向量、RRF、交叉编码器 rerank、知识图谱和 Text2SQL，前两者中的 RRF 与 ES 检索不在当前实现中。

- **Q：你说“用了向量数据库 + topK 召回 + rerank”，为什么这样不够？**

  **A：【已实现】** 这套链路只保证“有候选并重新排序”，不能保证语料正确、切片合理、权限正确、问题被完整改写或答案忠于证据。还需要离线 Recall/MRR/nDCG、BM25 补充专有名词、metadata filter、去重、时效和可信度、答案 groundedness 检查以及失败归因。

### 6.2 切分与召回

- **Q：原始文档是怎么切 Chunk 的？Chunk Size 和 overlap 多少？怎么确定？**

  **A：【部分实现】** Python 约 500 字切片，按句号/换行尽量保持语义，当前没有固定 overlap；Java 使用最多 500 个 Unicode 码点和最多 80 码点重叠，优先在后半段找句末或换行。数字是为长度控制设置的工程值，仓库没有参数扫描证明最优。

- **Q：RAG 中切块是越大越好吗？**

  **A：【已实现】** 不是。块大上下文完整但噪声多、向量主题被稀释、Top-K 浪费预算；块小定位准但事实可能被切断。项目用约 500 单位并尽量按句边界处理，其他语料应通过 Recall@K、答案完整性和引用准确率实验决定。

- **Q：RAG 召回不准，从哪查？**

  **A：【已实现】** 按“语料与权限 → 切片 → embedding → 索引版本 → query rewrite → 初召回 → 融合/rerank → Top-K 装配 → 生成”逐层查。Java RAG 评测器已能把失败归因到 retrieval miss、partial miss、agent skipped retrieval、grounding failure 等阶段；当前还不能区分初召回失败与重排淘汰。

- **Q：召回率、精确率怎么算？混合召回如何融合分数？**

  **A：【已实现】** `Precision@K = Top-K 中相关片段数 / K`，`Recall@K = Top-K 中相关片段数 / 全部相关片段数`。Java 项目把 BM25 和向量分数分别归一化，再按配置权重加权求和，不是 RRF。融合参数需要在固定语料上评测。

- **Q：RRF 具体是怎么做的？融合是等权的吗？提升主要来自哪类问题的修复？**

  **A：【项目未涉及】** RRF 对每路排名计算 `score(d)=Σ 1/(k+rank_i(d))`，通常 `k=60`，只看排名不看原始分数，因此天然避免不同检索器分数量纲问题；各路通常等权，也可加权重。它主要修复单个检索器排序不稳定、专有名词与语义互补的问题。EchoMind 当前没有 RRF。

- **Q：为什么检索要用 BM25 + Dense Retrieval，只用 Dense 不行吗？**

  **A：【部分实现】** Python 主要使用 Dense；Java 已使用 BM25+Dense。Dense 擅长语义改写，但可能漏掉订单号、错误码、产品型号等精确词；BM25 擅长词面匹配但不懂同义表达。混合检索是互补关系，不保证一定提升，需按业务集验证。

- **Q：混合检索怎么体现？向量检索不是只有 Redis 吗？**

  **A：【已实现】** EchoMind 不使用 Redis 做向量检索，Redis 主要保存会话、锁、回执和轨迹。Java 在应用内构建 BM25 并和向量存储分数融合；Python 使用 Chroma 向量召回。面试时不能把项目的 Chroma 说成 Redis 向量。

- **Q：为什么要同时做 Redis 向量检索和 ES 检索？**

  **A：【项目未涉及】** 项目没有 Redis 向量和 ES。通用理由可以是 Redis 提供低延迟向量查询，ES 提供成熟 BM25、过滤和聚合；但维护两套索引会增加一致性、成本和运维复杂度，应该按规模选择，而不是默认双写。

- **Q：不选 ES 向量检索是为了防止 ES 崩后整条检索链路崩溃？**

  **A：【项目未涉及】** 这不是项目的设计理由。单靠增加另一个存储不能自动避免级联故障，还需要超时、熔断、降级和一致性策略。EchoMind 选择 Chroma/本地语义存储主要是集成成本；没有用 ES，也就没有这项对比结论。

### 6.3 知识库工程

- **Q：你是否负责知识库相关开发？是否对接知识库索引、清洗、API/MCP？**

  **A：【已实现】** 项目包含知识库导入、切片、Chroma/语义索引、更新删除、REST API、MCP Server 和 MCP Client 调用。清洗主要是格式、空内容、大小和切片处理，未实现企业级 OCR、去重、权限和复杂文档解析流水线。

- **Q：知识库的核心设计要点是什么？Agent 应用中如何用好知识库？**

  **A：【已实现】** 核心是稳定文档身份、增量更新、权限与租户隔离、可观测切片、混合召回、版本与缓存一致性、证据引用和评测。Agent 应按需检索、用工具结果约束回答、资料不足时明确说明，而不是每轮无脑把 Top-K 塞入上下文。

- **Q：知识库文档更新，怎么不重建全量？**

  **A：【已实现】** 使用显式 `document_id` 或标题生成稳定文档身份，以“文档身份+片段序号”作为片段 ID，内容哈希作为版本。重导入时 upsert 新片段、删除多余旧片段并清理检索缓存，不会重建整个知识库。

- **Q：RAG 检索回来的文档带幻觉内容，Agent 为什么会信？怎么拦截？**

  **A：【部分实现】** 模型通常把检索内容当作高可信上下文，若资料本身错误、过时或含恶意指令，就可能照用。Java 版有基于上下文的 groundedness 校验，但校验器本身也是 LLM，不是绝对可靠。生产上要控制资料发布权限、来源可信度、时效和版本，隔离“资料内容”和“系统指令”，并在高风险动作前做确定性业务核验。

- **Q：RAG 主要存在哪些问题？如何进一步提升效果？**

  **A：【已实现】** 主要包括语料质量、切片边界、领域 embedding、查询改写、精确词召回、rerank、Top-K 噪声、时效和引用问题。提升应先用评测定位阶段，再选择混合检索、metadata filter、rerank、分层摘要和 grounded answer，而不是只换更大 embedding。

### 6.4 与其他方案对比

- **Q：RAG 和知识图谱对比，旅游场景分别适合什么？**

  **A：【项目未涉及】** RAG 适合政策、攻略、描述类长文本；知识图谱适合机场、航线、景点、交通关系及多跳约束。旅游系统可先 SQL/图谱处理行程约束和库存，再用 RAG 解释政策与推荐理由。

- **Q：Text2SQL 怎么做校验，如何防注入？**

  **A：【项目未涉及】** 模型只生成只读查询，后端用 AST 白名单限制 SELECT 和表/列，禁止 DDL/DML、注释逃逸和多语句；使用参数化、行级权限、租户过滤、超时和 LIMIT。执行前 explain dry-run，结果再校验，不能只靠 Prompt 防注入。

- **Q：新接入一个 MCP 或 Skill，怎么保证它不会拉低整体指标？**

  **A：【部分实现】** 项目有白名单、角色范围、只读声明和回归评测，但没有完整上线门禁。稳妥流程是先离线跑全量回归 + 新能力专项集，再影子流量和小流量 canary，观察触发率、成功率、误触发、延迟、成本和下游业务指标，异常自动摘除。

### 6.5 RAG 评测

- **Q：RAG 的评测集有多少条？**

  **A：【已实现】** Java 仓库有一套 10 篇演示文档、26 个问题的 RAG v1 数据集，覆盖单文档、多跳和不可回答样本，Top-K=5。它不是生产规模评测集。

- **Q：MRR（平均倒数排名）是怎么计算的？**

  **A：【已实现】** 对每个问题找到第一个相关片段的排名 `r`，该问题得分 `1/r`；没有命中得 0。所有问题取平均就是 MRR。它重视首个正确结果的位置，但不衡量是否找全全部相关片段。

- **Q：RAG 指标是怎么一步步提上来的？最开始是多少？怎么发现问题、怎么改的？**

  **A：【已实现】** 仓库记录了一次小样本对照：无模型改写时 Recall@5 为 0.9583、nDCG@5 为 0.9644；启用查询改写后一次运行达到 Recall@5 1.0000、nDCG@5 0.9904。该结果来自 26 条固定小样本，且业务标签仍待专家复核，不能外推为生产提升。

## 七、评测与可观测性

### 7.1 评测体系

- **Q：如何评估 Agent？缺少用户反馈时怎么抽检？规划能力与幻觉率如何权衡？**

  **A：【部分实现】** EchoMind 用意图 Accuracy/Macro-F1、路由/工具/实体确定性断言、RAG Recall/MRR/nDCG 和 LLM-as-Judge 四维质量评分。缺少用户反馈时可使用专家标注回归集、线上 trace 分层抽样和失败样本回流。规划能力与幻觉率是分开的指标：不能为了完成任务而编造动作成功，高风险任务宁愿升级也不能猜。

- **Q：一套完整 Agent 评估体系需要搭建什么？为什么任务成功率不能作为唯一指标？**

  **A：【部分实现】** 项目覆盖意图、路由、工具、回答质量、RAG 检索、延迟、成本和回归基线，但未覆盖真实业务成功率和用户满意度。任务成功率可能掩盖越权、错误引用、高延迟、高成本、只成功简单样本或“模型自称完成”等风险，因此需要分层指标。

- **Q：Agent 整体有哪些评估指标，线上怎么持续评测？**

  **A：【部分实现】** 离线有 Accuracy、Macro-F1、Recall@K、MRR、nDCG、通过率和 Judge 四维分；线上有响应状态、Agent/工具成功率、延迟、熔断和 trace。持续评测应定时跑冻结回归集、对新请求抽样评分、监控数据漂移，并对新版本做 shadow/canary。

- **Q：怎么评估 Agent 效果？**

  **A：【已实现】** 先确认真实调用 Orchestrator，再分为可确定检查的部分和主观质量部分。角色、意图、必需工具、实体、执行状态由代码断言；回答相关性、准确性、完整性和有用性交给带参考答案/证据的 Judge。执行失败、部分成功和评分失败分别记录，不能混成同一个通过率。

- **Q：整个项目的评测怎么做的？从数据收集到最终指标的流程是什么？**

  **A：【已实现】** 收集并标注问题、历史、期望意图/Agent/工具/实体、参考答案和证据 → 运行固定用例 → 计算确定性检查与 Judge 分数 → 汇总报告 → 与相同 `suite_id` 的完整基线比较 → 回退超过 5% 的指标 → 将 bad case 回流测试集或修复逻辑。

- **Q：你的指标都是端到端的吧？有没有考虑流程评估——能自动定位失败在意图、检索还是生成？**

  **A：【已实现】** 有过程评估。意图评测单独计算分类指标，对话用例检查主 Agent、意图、必需工具和实体；RAG 评测按检索命中、Agent 是否使用知识、回答是否 grounded、质量是否达标做阶段归因。当前 RAG 归因还不能区分初召回失败与重排淘汰。

- **Q：了解 Agent 评测 case 吗（包含输入输出、预期行为、证据和评分规则）？**

  **A：【已实现】** 项目用例包含输入和历史、期望 Agent/意图/工具/实体、参考答案、证据、确定性断言以及 Judge 四维评分。Fisher 风格的完整 case 还应包含风险等级、禁止行为、允许的工具范围和最终业务状态。

- **Q：从头设计一个 Agent 评测集。**

  **A：【项目未涉及】** 应先从线上/业务需求建 taxonomy，再覆盖正常、边界、多轮、冲突、权限、故障和不可回答样本；每个样本标注期望控制流、最小证据、禁止行为和成本上限；再划分开发/回归/盲测集，固定数据版本和评分脚本，避免针对测试集调参。

- **Q：RAG 和 memory 怎么评测？**

  **A：【部分实现】** RAG 项目有 26 条固定小样本和检索指标；memory 尚无独立 benchmark。RAG 应测检索召回、排序、答案 groundedness 和闭环使用率；memory 应测跨轮/跨会话事实召回、冲突更新、作用域隔离、遗忘和噪声抑制。

- **Q：Skill 评测集如何构建？只更新单个 Skill 时如何验证整体业务会不会劣化？**

  **A：【部分实现】** 项目有 Agent/RAG 回归但无独立 Skill 套件。应为每个 Skill 建触发、不触发、边界、冲突和禁止行为用例，再加业务全量回归；新版 Skill 先跑相同 `suite_id` 对比，再做 canary 和回滚。

- **Q：举一个评测集样例，问题和答案分别是什么形式？**

  **A：【已实现】** 例如问题“登录一直报 401”，期望 Agent 为 `technical`、意图为 `technical_login`、实体含错误码 401，参考答案是检查登录状态、Token 有效期和权限且不索要密码，证据来自错误码工具说明；代码检查路由和实体，Judge 检查回答质量。

- **Q：Skill 如何管理、更新，如何评估更新后的效果好坏？**

  **A：【部分实现】** 当前用目录文件、热加载、启用标志、角色和关键词管理，修改后可调用 reload。缺少版本审批和自动灰度；评估要覆盖触发准确率、任务遵守率、冲突、安全拒绝、回答质量和成本，并保留可回滚旧版本。

### 7.2 Bad Case 归因

- **Q：Bad Case 如何定位到规划、工具、参数还是推理？如何回流优化并防止回归？**

  **A：【部分实现】** 项目 trace 能看意图、路由、工具名/参数、成功状态、result success、延迟、缓存、重排和降级；评测可检查期望 Agent、意图、工具和实体。当前没有独立 Planner，因此不能把失败简单归因到“规划”。修复后加入相同 suite 回归，记录代码、配置、Skill 和语料版本。

- **Q：意图识别怎么评估，Badcase 怎么回流？**

  **A：【已实现】** 用带历史上下文的标注集计算 Accuracy、per-class Precision/Recall/F1 和 Macro-F1。错分样本要检查 LLM、Embedding、Pattern 三路分别输出什么；修复关键词/模板/提示或阈值后加回回归集。

- **Q：某个任务成功率低，怎么分析和优化？**

  **A：【部分实现】** 先按意图、Agent、工具、输入长度、状态、时延和错误码切片，确认失败是模型、检索、工具、权限、超时还是评分问题；再导出 trace 和真实输出人工复核。每项优化只改一个变量，用相同数据集比较通过率、延迟和成本。

- **Q：你用过 LangFuse 吧？LangFuse 如何排查 bad case？**

  **A：【项目未涉及】** EchoMind 使用自有 Redis trace、Prometheus 和评测报告，没有集成 LangFuse。LangFuse 类系统一般按 trace/span 查看每轮模型、工具、耗时和成本，再筛选失败评分样本，构建数据集回归；具体用法不应冒充项目经验。

- **Q：新接入工具/技能后怎么防止整体指标回退？**

  **A：【部分实现】** 项目有工具白名单和回归评测，但上线门禁需补强。应采用“专项集验证 + 全量回归 + shadow + canary”，监控误触发率、成功率、延迟和成本；保留一键摘除和旧版本回滚。

### 7.3 上线判断

- **Q：怎么区分一个 Agent 是真正能上线生产，还是仅仅能跑通 Demo？**

  **A：【部分实现】** 项目具备鉴权、会话锁、回执、超时、熔断、trace、评测和 Docker 部署，比纯 Demo 完整；但当前没有真实订单/退款业务、压测数据和用户效果。生产判断要看真实依赖接入、权限审计、幂等、故障恢复、容量、成本、灰度和持续评测，而不是只看一次回答流畅。

- **Q：怎么评估 Agent 对原有人工分析流程的价值？**

  **A：【项目未涉及】** 应做与人工基线的前后对照：处理时长、一次解决率、返工率、错误率、覆盖率、单任务成本、人工接管率和用户满意度。采用影子运行和 A/B，避免只用“生成了多少内容”衡量。

- **Q：你遇到了什么问题？为什么这么解决？怎么验证有效？**

  **A：【已实现】** 可回答项目实际处理的并发压缩覆盖、旧请求覆盖新熔断、写工具结果未知、工具失败被误当知识证据等问题。解决方式是快照版本、generation、副作用前置回执和 success 语义分离；验证靠仓库中的单元、竞态和集成测试。不要编造未验证的业务收益。

## 八、工程稳定性与系统设计

### 8.1 失败恢复与幂等

- **Q：Agent 支持从 SQLite 恢复。若有副作用工具已成功，但状态写 SQLite 前崩溃，怎么保证不重复执行？**

  **A：【项目未涉及】** EchoMind 不使用 SQLite。正确做法是在执行前持久化 `step=PENDING` 和幂等键，再调用外部系统；外部成功与本地成功无法靠本地事务原子化，因此必须让远端支持同一个幂等键和结果查询。重启后状态为 UNKNOWN 时先查结果，绝不自动重放。

- **Q：服务端已接收任务，但客户端超时重启，保存哪些状态、怎么恢复任务？**

  **A：【已实现】** 项目保存 `client_request_id`、会话、执行状态、回执、业务 state 和 trace；相同 ID 重试若已成功直接返回回执，可重试失败才重新执行。真实长任务还需持久化 `run_id`、当前节点、输出 artifact、取消状态和恢复游标。

- **Q：子任务失败如何重试、降级？无人值守时如何验证任务真正完成？**

  **A：【部分实现】** 项目只在整轮有失败回退、工具熔断和可重试标记，没有通用子任务重试。应按错误类别和幂等性重试，失败后降级为安全替代或人工；完成验证要依赖每个节点的确定性输出和外部状态查询。

- **Q：长任务失败、恢复、取消、错误处理。**

  **A：【项目未涉及】** 需要持久化 DAG/状态机、lease/fencing、checkpoint、取消传播和补偿。EchoMind 当前最大执行单位是一轮聊天，评测任务最多运行 1800 秒且重启后丢失任务进度。

- **Q：如果一个 Agent 执行失败，系统怎么处理？**

  **A：【已实现】** 专业 Agent 失败会回退 General；所有 Agent 失败返回 failed/503；多 Agent 只有部分成功返回 partial；写工具尝试后禁止自动交给另一个 Agent 重做；Java 校验不合格则转人工或返回可重试失败。

- **Q：大模型调用超时重试，如何避免重复调用工具？**

  **A：【已实现】** 项目按 `client_request_id` 复用回执，副作用工具调用前写入不可重放标记，同一请求中相同工具和参数只执行一次。模型超时不应直接重跑整个副作用步骤；必须先从 trace/业务结果确认是否已执行。

### 8.2 限流与权限

- **Q：限流怎么做？用户级、会话级、工具级分别怎么设计？**

  **A：【项目未涉及】** 当前没有生产限流，只有评测队列容量和部分长度/次数限制。通用实现可用 Redis Token Bucket：用户级控制总预算，会话级控制并行和速率，工具级按下游容量、成本和风险限流；429 返回 retry-after，并对高风险工具设置更低配额。

- **Q：权限控制、防越权。**

  **A：【已实现】** 项目支持 API Bearer Token、用户/管理员角色、服务端覆盖 `user_id`、知识写入/评测/监控等管理权限，角色工具也有白名单。共享知识库还不是租户级隔离；真实业务系统必须在工具 handler 和服务端再次校验资源归属。

- **Q：权限、审计和安全兜底怎么做？**

  **A：【部分实现】** 有鉴权、角色、工具白名单、脱敏 trace、写操作前置回执和只读 MCP。完整方案还要租户隔离、细粒度 scope、不可篡改审计、敏感字段脱敏、审批流、异常检测和数据删除能力。

### 8.3 安全

- **Q：金融 Agent 的提示注入风险：用户账单里藏恶意指令怎么防？**

  **A：【部分实现】** 项目没有针对金融账单的完整防注入模块。通用方案是账单内容只作为数据块交给模型，系统提示明确禁止执行文档指令；工具参数只来自可信 Schema，金额/账户/收款方由服务端从订单系统注入，任何转账类动作必须人工确认和双因素校验。

- **Q：Agent 读取本地文档，文档内包含窃取凭证、发邮件这类恶意指令，从哪些层面拦截防护？**

  **A：【部分实现】** 项目通过只读 MCP、角色白名单、结果大小限制和工具参数校验缩小能力面。还需文档沙箱解析、内容净化、系统/资料指令隔离、敏感文件禁读、网络发送白名单、无凭证环境、动作审批和审计；不能只依赖“请忽略恶意指令”的 Prompt。

- **Q：MCP Server 需要考虑哪些安全问题？**

  **A：【部分实现】** 详见 1.2。项目已有白名单、只读声明、超时和鉴权，仍需补齐 OAuth Scope、租户隔离、SSRF/命令注入、MCP 返回内容注入、限流、审计和沙箱。

### 8.4 并发与异步

- **Q：Agent 属于 IO 还是 CPU 密集？线程池怎么设计？**

  **A：【已实现】** 主链路主要是网络和存储 IO：LLM、Redis、Chroma、MCP。Python 使用 `asyncio`，同步向量库操作放到 `to_thread`；Java 用线程池/框架执行阻塞模型和工具调用。线程池应按下游类型隔离，避免慢工具占满所有 worker，并设置队列上限和拒绝策略。

- **Q：Python asyncio 多调用场景，怎么设计 trace ID？子 Agent 怎么传递？**

  **A：【已实现】** 项目有服务端 `request_id`，工具轨迹按请求返回并持久化；不同 Agent 的工具轨迹通过局部结果对象隔离。多任务传播可使用 `contextvars` 保存 trace/span/parent ID，显式创建 task 时复制 context，并让子 Agent 使用 `parent_span_id`。

- **Q：Kafka 在 Agent 链路里能承担什么角色？工具异步执行怎么保证顺序？**

  **A：【项目未涉及】** 项目没有 Kafka。Kafka 可用于长任务、事件日志、工具异步执行和跨服务解耦；顺序应按 `conversation_id` 或 `resource_id` 作为 partition key，消费端用业务序号、状态机和幂等键处理乱序和重复。

- **Q：Redis 除了缓存，还能在 Agent 场景支撑哪些能力？**

  **A：【已实现】** EchoMind 用 Redis 保存工作记忆、摘要、业务状态、请求回执、会话租约锁、轨迹索引和画像更新锁。还可实现限流、任务队列、短期事件流和分布式信号。

- **Q：MySQL 怎么设计一张 Agent 执行轨迹表？字段怎么定？**

  **A：【项目未涉及】** 可按 span 建表：`trace_id`、`span_id`、`parent_span_id`、`request_id`、`user_hash`、`conv_id`、`agent_type`、`stage`、`tool_name`、`input_hash`、`status`、`error_code`、`latency_ms`、`token_in/out`、`model`、`started_at`、`finished_at`。原始敏感参数不要明文存储，另设脱敏/受控证据表。

- **Q：MySQL、Redis、ES 的多存储一致性怎么实现？这三个服务的分布式事务真的能实现吗？有必要实现吗？**

  **A：【项目未涉及】** 一般不做跨 MySQL/Redis/ES 的强分布式事务。MySQL 作为事实源，使用 outbox/CDC 异步更新 Redis 和 ES；缓存可丢、可重建，搜索索引允许短暂延迟。对必须一致的读路径加版本检查和重试，通过补偿与对账实现最终一致，而不是强求三阶段提交。

### 8.5 状态与编排

- **Q：LangGraph 里 state、node、edge、checkpoint 分别解决什么问题？**

  **A：【项目未涉及】** `state` 是图中共享的可版本化数据，`node` 是处理步骤，`edge` 决定下一步和分支，`checkpoint` 保存执行位置和状态以支持恢复、重放和人工介入。EchoMind 有请求 state 和 Redis 提交，但没有逐步图 checkpoint。

- **Q：LangGraph 用了哪些组件？状态流转和 Checkpoint 如何实现？为何不选其他方案？**

  **A：【项目未涉及】** EchoMind 没有使用 LangGraph。不能把普通 Orchestrator 说成 LangGraph。选型时应比较团队熟悉度、持久化、分支/并行、恢复和可观测性；当前项目选择自研编排以明确控制会话、工具和回执边界，Java 则使用 Spring + LangChain4j。

- **Q：LangChain 和 LangGraph 有什么区别？**

  **A：【项目未涉及】** LangChain 更偏向模型、消息、工具、检索等应用组件组合；LangGraph 更偏向有状态、可循环、可 checkpoint 的图式编排。EchoMind Python 自研编排，Java 使用 LangChain4j，不是 LangGraph。

- **Q：Agent 同时接收语音、文本、工具结果时，怎么设计状态机？**

  **A：【项目未涉及】** 详见 5.4。核心是单会话事件队列、单调序号、run ID、FSM 状态、事件去重和过期过滤。

- **Q：Agent 部署在哪里？**

  **A：【已实现】** FastAPI 和 Spring Boot 服务通过 Docker Compose 部署，依赖 Redis、Chroma、Prometheus 和 Nginx；Python 主链路由单进程运行，评测任务和部分状态在进程内。

- **Q：医疗 Agent 是独立系统，还是搭建在 Agent 平台之上？**

  **A：【项目未涉及】** EchoMind 是客服原型，不是医疗系统。通用医疗 Agent 应建设在受控平台上，复用身份、审计、知识库、工具治理和评测，但分诊、用药和病历必须有独立合规边界与人工复核。

### 8.6 Harness / 框架

- **Q：你的 Harness 有哪些模块？分别做什么？**

  **A：【已实现】** EchoMind 是自定义 Harness，包含入口鉴权、会话锁、上下文装配、意图路由、Agent/Tool Loop、MCP、记忆、trace、monitor、评测和部署。每个模块都有独立失败语义。

- **Q：为什么自己从零开发，而不用现有框架？**

  **A：【部分实现】** Python 自研编排是为了明确控制整轮提交、Redis 租约、副作用前置回执和评测隔离；Java 则采用 Spring + LangChain4j。不是说不用框架更高级，而是当前项目需要把这些边界作为核心可验证代码；若需求标准化，框架能显著降低维护成本。

- **Q：Harness 是什么？Agent Harness 分几块？**

  **A：【部分实现】** Harness 是围绕模型的执行外壳，负责上下文、工具、循环、状态、权限、恢复、观测和评测。没有公认统一阶段划分，不应在面试中编造“第几代”。EchoMind 可作为自定义 Harness 例子说明各模块。

- **Q：同样一个大模型，放到不同 Harness 里成功率差异很大，你怎么理解？**

  **A：【已实现】** 模型只是决策器，Harness 决定它看到什么、能调用什么、何时停止、怎样校验和恢复。工具 Schema、上下文质量、错误反馈、预算和状态一致性都会改变最终成功率。

- **Q：了解某个“一切皆插件”的 Agent 框架吗？用它也能做到全程透明，为什么不用？**

  **A：【项目未涉及】** 不能声称熟悉未接入的具体框架。通用上，“插件化”降低扩展成本但不自动提供可靠会话提交、权限隔离、checkpoint 和评测；选型要看这些生产能力，而不是只看插件生态。

- **Q：把 OpenClaw 这类开源 Agent 框架迁移到生产，优先补齐哪些能力？**

  **A：【项目未涉及】** EchoMind 没有集成 OpenClaw。迁移到生产应优先补身份/租户、工具权限、密钥、沙箱、预算和限流、幂等与恢复、审计、回归评测、灰度回滚及数据合规。

- **Q：最近有没有看 Harness/Agent 相关开源项目、论文？**

  **A：【项目未涉及】** 回答时应只提真正读过的资料。可围绕 Tool Use、ReAct、Plan-Execute、context engineering、agent evaluation、MCP 和 long-running task recovery 讨论，不要把 EchoMind 未实现的能力说成论文复现。

- **Q：你有读过一些主流 Agent 的源码吗？**

  **A：【部分实现】** 本项目源码已系统梳理；未接入的 Claude Code、OpenClaw、Hermes 等不应声称读过全部源码。可以诚实回答“产品设计层面了解、项目未做源码级复刻”。

- **Q：之前比较火的“hermes”Agent 框架，听过吗？最大亮点是什么？**

  **A：【项目未涉及】** EchoMind 没有使用 Hermes，不能给出未验证的源码级结论。面试中可说明需要先确认对方指的是哪一个同名项目，再围绕工具协议、运行时和状态管理讨论。

- **Q：你觉得 Claude Code 的亮点是什么？有看过它的设计吗？**

  **A：【项目未涉及】** EchoMind 没有复刻 Claude Code。公开产品层面值得借鉴的是仓库探索、工具执行、上下文压缩、权限确认和长任务交互；具体内部机制不应臆测。

- **Q：你做的这个是类 Claude Code 或 Codex 吗？**

  **A：【部分实现】** 不是。EchoMind 是客服多 Agent 编排，具有有界工具循环，但没有代码编辑、shell 沙箱、仓库级长期任务和 checkpoint，不应包装成 coding agent。

## 九、模型基础与选型

- **Q：用的哪个模型？为什么选它？和其他模型做过横向对比吗？**

  **A：【部分实现】** 项目支持 Anthropic 与 DeepSeek 的 Anthropic Messages 兼容调用，Java 使用 LangChain4j 的 `AnthropicChatModel`。选择重点是工具调用兼容、中文客服效果和部署便利，但仓库没有同一业务集上的受控模型横向对比，因此不能回答“某模型效果提升 X%”。面试时只能说明兼容性、成本和现有评测结果，不能把厂商宣传当项目结论。

- **Q：如果换一个底层大模型，整个 Agent 架构需要改多少？**

  **A：【部分实现】** Java 通过 LangChain4j 抽象，Python 依赖 Anthropic Messages 兼容协议，路由、记忆、状态和业务工具相对独立；但 Prompt、工具 Schema、token 估算、截断行为、结构化输出稳定性和模型延迟仍需重新验证。不能认为替换 model ID 就等于完成迁移。

- **Q：主 Agent/子 Agent 如何分配模型？为什么不建议全部用同一个大模型？**

  **A：【部分实现】** EchoMind 允许 General、Technical、Billing 分别通过环境变量指定模型，但默认可共用同一 provider。可按任务复杂度、工具风险、延迟和成本分层：简单分诊用小型模型，复杂排障用较强模型，安全校验使用独立模型或规则。全部用大模型并非错误，关键是收益是否覆盖成本，并通过评测验证。

- **Q：temperature 和 top-p 有什么区别？**

  **A：【项目未涉及原理题】** temperature 调整 logits 分布的平滑程度，越低越确定；top-p 只保留累计概率达到阈值的候选集合，再从中采样。两者都影响随机性，通常会调一个而保持另一个为默认值。

- **Q：temperature 设为 0 能完全复现输出吗？**

  **A：【项目未涉及原理题】** 一般不能保证逐字复现。temperature=0 通常接近贪心解码，但服务端批处理、浮点差异、硬件核、MoE 路由、上下文变化和供应商实现都可能造成微小差异。需要强确定性时，应保存结构化结果和缓存，而不是依赖模型复现。

- **Q：KV Cache 是什么？**

  **A：【项目未涉及原理题】** Transformer 自回归生成时，每层历史 token 的 Key/Value 张量可以复用，避免每一步重新计算全部前缀。它显著降低时延和算力，但占用显存，且只有相同前缀才容易复用。EchoMind 没有自研推理引擎，也未统计供应商 KV/Prompt Cache 命中率。

- **Q：BERT、Transformer、Self-Attention。**

  **A：【项目未涉及原理题】** Transformer 是使用自注意力等结构建模序列的神经网络架构；Self-Attention 让每个 token 根据与其他 token 的相关性聚合信息。BERT 是双向 Transformer Encoder，训练目标包含 Masked Language Model，适合表示和分类；GPT 类模型是自回归 Decoder，适合生成。

- **Q：LM 大模型 API 是有状态还是无状态？为什么要持续追加历史消息？**

  **A：【已实现】** 应用层 API 通常无状态，服务端缓存不等于业务状态。EchoMind 每轮显式传入摘要、最近历史、结构化字段和当前消息；多轮记忆由 Redis/Chroma 管理。即使供应商做前缀缓存，也不能依赖它保存会话事实。

- **Q：最近几个月关注了哪些 AI 新技术？**

  **A：【项目未涉及】** 可回答与项目直接相关且确实了解的方向：MCP 工具互操作、Agent evaluation、结构化输出、上下文工程、长任务 checkpoint、代码/终端沙箱和可观测性。不要把未验证的新论文或产品说成已落地。

- **Q：你怎么理解 VibeCoding 这个工具？在 Agent 开发场景下你会怎么用？**

  **A：【项目未涉及】** 可把它理解为通过自然语言快速生成和迭代代码的工作方式。Agent 开发中适合搭骨架、生成测试和定位重复代码，但必须用类型检查、测试、代码审查和真实运行验证约束；不能让模型生成的关键业务逻辑未经测试直接上线。

- **Q：平时写代码用什么 AI 编码工具，感受对比？**

  **A：【项目未涉及】** 应按实际经历回答。可评价的维度是仓库理解、跨文件修改、终端执行、测试修复、上下文压缩、可控性和隐私，不应只比较“生成代码快不快”。

### 语音 / 多模态

- **Q：流式 ASR 与非流式 ASR 的核心差异？线上业务只用非流式 ASR 可行吗？**

  **A：【项目未涉及】** 流式 ASR 在音频输入过程中持续输出部分结果，首包快、可打断；非流式通常等音频结束后一次性识别，准确率或实现更简单但等待更长。客服表单和录音转写可用非流式；需要实时交互的座舱、通话和语音 Agent 通常不能只依赖非流式。

- **Q：ASR 选型评估需要考量哪些维度？为什么不能只看字错率？**

- **Q：车载 Agent 在行车环境下做 Skill 调用有哪些额外约束？**

  **A：【项目未涉及】** 必须低时延、可打断、免手操作、抗噪，避免长文本和高认知负担；驾驶相关操作必须按风险分级，导航、空调等可执行，支付、解锁、安全控制等需硬确认或禁止；还要有离线降级和网络中断保护。

## 十、业务场景设计题

- **Q：有大量车辆质量问题记录，业务专家问“最近空调不制冷的问题变多了，能不能找到相关案例并辅助生成问题描述”，这个 Agent 怎么设计？**

  **A：【项目未涉及】** 先把结构化字段（车型、年份、故障码、时间、地域、维修结果）入库，故障描述做全文和向量索引。Agent 先澄清时间窗口和比较基线，再调用趋势分析工具计算同比/环比、聚类和异常点，调用检索工具找相似案例，最后由模型生成带统计证据、案例引用的描述；发布前由业务专家审核。

- **Q：数据查询之前的那一步要做什么？Agent 什么时候该调用工具？什么时候该停止？什么时候需要人工确认？**

  **A：【项目未涉及】** 查询前要解析实体、时间、口径和权限，选择数据源并校验 Schema。需要权威事实或实时状态时调用工具；证据满足完成条件且校验通过时停止；不可逆写操作、高风险金额、权限不足、多条候选记录或证据冲突时需要人工确认。

- **Q：要实现情感分类、文本总结等算法接口，实时性/准确率/成本要求不同时，怎么做技术选型？**

  **A：【项目未涉及】** 用任务矩阵选型：高频固定标签优先规则或小型微调模型，长尾和解释型任务用 LLM；实时低延迟用轻量模型或流式接口，离线高准确率可用大模型+人工复核；成本敏感场景做置信度路由，高置信走小模型，低置信升级。

- **Q：淘宝有千万级用户评论，要划为正面/中性/负面，要求速度快成本低，采用什么方案？**

  **A：【项目未涉及】** 优先训练小型中文分类模型或使用 embedding + 轻量分类头，批处理离线推理；先做去重、语言识别和规则处理，再用主动学习补充难例。低置信度或含反讽的样本送给大模型/人工复核，不宜逐条调用大模型。

- **Q：设计一个多业务方接入的日志分析与异常告警系统，整个系统怎么设计？**

  **A：【项目未涉及】** 采集侧统一 SDK/Agent，消息总线按业务分区，处理层做 Schema 归一化、脱敏、聚合、规则和异常检测，存储层按场景使用对象存储、搜索和时序库；告警层做去重、抑制、升级和值班路由；LLM 只负责解释、聚类摘要和辅助 RCA，不能替代确定性阈值和权限。

- **Q：不同业务错误含义不同，怎么利用大模型针对不同业务做分析？**

  **A：【项目未涉及】** 为每个租户建立错误码、日志模板和业务知识库，检索时强制按业务/服务/版本过滤；模型输出必须引用日志片段和错误码定义。用规则先做明确分类，LLM 处理语义归纳，低置信或高风险事件交人工确认。

- **Q：接入 10~20 个业务方，不同业务的 Skill 应该由平台方写还是业务方提供？**

  **A：【项目未涉及】** 平台方提供 Skill 规范、SDK、Schema、权限和评测工具；业务方维护领域知识、错误码、处理 SOP 和验收用例；平台审核发布。这样既保证统一治理，又避免平台团队成为所有业务知识瓶颈。

- **Q：业务方把代码库也接入系统，怎么结合代码库分析定位日志异常？**

  **A：【项目未涉及】** 把日志中的服务名、版本、commit、trace ID、异常栈与代码图关联；建立符号、调用关系和服务依赖索引，Agent 先用日志定位异常点，再检索对应函数、最近 diff 和相关测试，输出证据链。

- **Q：一个业务有四五个微服务、多个仓库，异常可能跨仓库，怎么分析仓库关系？代码十万行、目录七八层，怎么解决检索效率？**

  **A：【项目未涉及】** 建服务依赖图、OpenAPI/消息 Schema 和跨仓 trace 关联；代码按文件/函数切片，维护 AST 符号表和调用图，检索采用 BM25+向量+符号过滤，只把相关代码块交给模型。按仓库/服务建立缓存和增量索引，不把全部源码塞进上下文。

- **Q：医疗 Agent 除分诊、用药查询还有哪些业务场景？哪些是复杂场景？**

  **A：【项目未涉及】** 还包括预约、检查报告解释、慢病随访、保险理赔、病历摘要和健康教育。复杂场景是多病共存、药物相互作用、急危重症、儿童/孕产妇、跨机构病历和用药调整；这些必须有人类医生复核，不能由模型独立决策。

- **Q：淘宝/O2O 场景：从用户点击到后端处理、数据库存储、结果返回，整个数据流向是怎样的？**

  **A：【项目未涉及】** 客户端/CDN → API 网关 → 鉴权与限流 → 业务服务 → 缓存/数据库 → 消息队列异步处理 → 结果聚合 → 返回客户端；关键交易需要事务、幂等和最终一致，读取侧可使用缓存和搜索。Agent 只是业务服务的一个调用方，不替代交易系统。

- **Q：Agent 写分析脚本出错怎么校验？**

  **A：【项目未涉及】** 脚本必须在沙箱中以最小权限运行，先做语法/类型/依赖检查和小样本 dry-run，再对输出做 Schema、边界和统计合理性校验；限制网络、文件、资源和执行时间，禁止生产凭证，关键结果人工复核。

## 十一、后端八股

- **Q：简单讲一下 HTTP 协议。**

  **A：【项目未涉及原理题】** HTTP 是应用层请求/响应协议，包含方法、URL、版本、Header、Body 和状态码；业务通常无状态，依靠 Cookie/Token 维持身份。HTTP/1.1 支持持久连接和管线化，HTTP/2 做多路复用和头部压缩。

- **Q：HTTPS 主要解决什么问题？为什么用 HTTPS？它和 HTTP 有什么区别？**

  **A：【项目未涉及原理题】** HTTPS 在 HTTP 下增加 TLS，解决传输加密、服务端身份认证和消息完整性，防止窃听、篡改和冒充。HTTP 明文，HTTPS 需要证书和握手成本；生产接口必须使用 HTTPS。

- **Q：你们后端是直接访问 MySQL，还是中间还有 Redis、消息队列？整个系统层次怎么构建？**

  **A：【项目未涉及】** EchoMind 当前没有 MySQL 或消息队列，主要使用 Redis 和 Chroma。一般系统是网关 → 应用服务 → 领域服务 → 缓存/数据库，异步任务通过消息队列解耦；Agent 服务不应绕过业务服务直接操作核心交易库。

- **Q：如果出现缓存雪崩，你会怎么处理？**

  **A：【项目未涉及】** 可做 TTL 抖动、多级缓存、热点预热、singleflight/互斥重建、熔断和限流、旧值 stale-while-revalidate、数据库保护和降级响应。缓存失效应按 key 分散，不能在同一时刻批量过期。

- **Q：关系型数据库和 Redis 分别适合存什么数据？**

  **A：【项目未涉及】** 关系型数据库适合有事务、一致性、约束和复杂查询的事实数据；Redis 适合低延迟缓存、短期状态、锁、计数、回执和队列。EchoMind 用 Redis 保存短期会话，但不能把 Redis 当成唯一业务事实源。

- **Q：系统以后除了优惠券还要接入优惠包等业务形态，怎么设计以支持不同场景接入？**

  **A：【项目未涉及】** 抽象统一的优惠能力接口：适用条件、计算、核销、退款和审计，用策略/插件注册不同形态；数据模型保存类型和扩展属性，调用方只依赖统一契约。新增类型通过配置和版本化接入，不能不断改主流程 if/else。

- **Q：APP 的 1.0、2.0 多版本同时存在但后台只有一套服务，怎么处理版本兼容？**

  **A：【项目未涉及】** 使用 URL/Header 版本或适配层，先做字段级兼容；旧客户端不认识的字段可忽略，新必填字段要提供默认或迁移期。采用 expand-migrate-contract，旧版本下线前保留兼容测试。

- **Q：2.0 版本数据库增加字段或新表，怎么保证 1.0 还能正常运行？**

  **A：【项目未涉及】** 新字段优先可空或有默认值，先双写/回填再切换读取；新表不要求旧逻辑访问，服务层做版本适配。避免重命名和立即删除旧列，按 expand→backfill→switch→contract 分阶段发布。

- **Q：不同服务的登录体系、权限粒度都不一样，怎么在当前系统中支持？**

  **A：【项目未涉及】** 建统一身份联邦和授权适配层：OIDC/SSO 获取可信身份，内部映射租户、角色和资源权限；各服务保留最小权限校验。不要只在网关做全局鉴权，业务服务仍需校验资源归属。

- **Q：设计一套完整的角色权限体系（普通用户、商家、超级管理员），怎么设计？**

  **A：【项目未涉及】** 采用 RBAC 为骨架、ABAC 处理资源和条件：用户-角色-权限，角色绑定菜单/API/操作；商家增加资源归属和租户范围，超级管理员走高风险审批和审计。权限在后端强制执行，前端隐藏按钮只是体验优化。

- **Q：操作系统 / Linux 基础。**

  **A：【项目未涉及】** 可覆盖进程/线程、上下文切换、内存分页与页缓存、文件描述符、socket、信号、调度、cgroup 和容器隔离。排查服务时常看 `top/ps/free/iostat/ss/lsof/dmesg`，结合 CPU、内存、IO、网络和句柄定位。

## 十二、手撕代码

### 12.1 最简 Agent 与工具调用系统

下面是一个不依赖框架的核心结构，面试时重点写清“模型输出工具请求、程序校验并执行、结果回传、预算终止”：

```python
from dataclasses import dataclass
from typing import Any, Callable


@dataclass(frozen=True)
class Tool:
    name: str
    schema: dict
    run: Callable[[dict], Any]
    retry_safe: bool = True


class Registry:
    def __init__(self) -> None:
        self.tools: dict[str, Tool] = {}

    def register(self, tool: Tool) -> None:
        self.tools[tool.name] = tool

    def execute(self, name: str, args: dict) -> dict:
        tool = self.tools.get(name)
        if tool is None:
            return {"success": False, "error": "unknown_tool"}
        try:
            return {"success": True, "data": tool.run(args)}
        except Exception as exc:
            return {
                "success": False,
                "error": type(exc).__name__,
                "retry_safe": tool.retry_safe,
            }


def agent_loop(llm, registry: Registry, messages: list[dict],
               max_steps: int = 4) -> str:
    for _ in range(max_steps):
        response = llm(messages, tools=[
            {"name": t.name, "schema": t.schema}
            for t in registry.tools.values()
        ])
        calls = response.get("tool_calls", [])
        if not calls:
            text = response.get("content", "").strip()
            if not text:
                raise RuntimeError("empty_response")
            return text
        messages.append({"role": "assistant", "tool_calls": calls})
        for call in calls:
            result = registry.execute(call["name"], call.get("arguments", {}))
            messages.append({
                "role": "tool",
                "tool_call_id": call["id"],
                "content": result,
            })
    raise RuntimeError("agent_step_budget_exceeded")
```

面试时还要补三点：真实实现必须有 JSON Schema、角色白名单、超时/熔断、副作用幂等和 trace；`retry_safe=False` 的工具执行前先持久化结果未知标记；模型只提出动作，权限和业务校验不能交给模型。

### 12.2 算法题

- **Q：反转链表（含单节点边界）。**

  **A：** 使用 `prev=null`、`cur=head`，逐个保存 `next` 并反转指针，时间 O(n)，空间 O(1)。单节点、空链表都要直接返回。

- **Q：岛屿数量（BFS）。**

  **A：** 遍历网格，遇到 `1` 就计数并从该位置 BFS，把访问过的陆地改成 `0` 或标记 visited；时间 O(mn)，空间最坏 O(mn)。

- **Q：第 K 个最大元素（要求 O(n)）。**

  **A：** 面试中先说明 min-heap 是 O(n log k)，若严格要求平均 O(n)，使用 Quickselect，随机选 pivot，Leiden 分区后只递归目标一侧；最坏 O(n²)，可以随机化降低概率。

- **Q：搜索插入位置（二分）。**

  **A：** 在 `[0,n]` 上二分第一个 `>= target` 的位置，返回 `left`；时间 O(log n)，空间 O(1)。

- **Q：排序链表（归并）。**

  **A：** 用快慢指针找中点，断开后递归排序左右链表，再合并；时间 O(n log n)，递归空间 O(log n)；要求 O(1) 空间时写自底向上归并。

- **Q：盛最多水的容器。**

  **A：** 左右双指针，面积由较短的边决定；每次移动较短的一侧，时间 O(n)，空间 O(1)。

- **Q：最长回文子串。**

  **A：** 枚举每个中心和每对中心，向两侧扩展，时间 O(n²)，空间 O(1)；也可用 Manacher 做到 O(n)。

- **Q：只出现一次的数字（其余出现两次）。**

  **A：** 全部数字做异或，成对数字抵消，结果就是唯一数字；时间 O(n)，空间 O(1)。

- **Q：判断是否是对称二叉树。**

  **A：** 递归比较左右子树的值，并交叉比较 `left.left` 与 `right.right`、`left.right` 与 `right.left`；也可用队列迭代。时间 O(n)，空间 O(h) 或队列宽度。

- **Q：拓扑排序。**

  **A：** 建图和入度，将所有入度 0 的节点入队；每次出队、加入结果并减少邻居入度，最终结果数不等于节点数说明有环。时间 O(V+E)，空间 O(V+E)。
